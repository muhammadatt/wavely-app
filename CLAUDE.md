## What This Project Is

**Instant Polish** is a browser-based audio editor targeting voice actors, audiobook narrators, podcasters, and anyone with an audio file that needs to sound better — no software download, no learning curve.

The core product loop: upload → process → hear the cleaned result in-browser → export (gated by tier).

**Design reference:** The Brain.FM ad (comparison-style marketing, before/after clarity, audience-specific proof points) is a useful visual framing model for marketing assets. The product itself follows a remove.bg model: universal task positioning, audience-specific intelligence delivered through presets.

---

## Usage Modes

The product serves three distinct user types. Architecture decisions must accommodate all three.

**Mode 1 — One-click preset user**
Upload → select preset → master → export. Editing is minimal or absent. The server-side preset chain is the entire product for them.

**Mode 2 — Edit-then-preset user**
Trim/cut/clean up the file first, then run the preset chain on the result. May apply spot operations (e.g. normalize a quiet passage) before mastering. The preset chain is still the final step.

**Mode 3 — Manual power user**
Builds their own processing chain through successive manual operations — noise reduction, normalize, compress applied to selections or the whole file, tweaked to taste. May never use presets, or uses them as a starting point and refines from there.

---

## Workflow Phases

Processing follows a natural two-phase flow:

**Phase 1 — Editorial**
Trim, cut, delete, silence regions, add silence, split. Spot processing (normalize, compress, noise reduce) applied to selections or the whole file. This is where the user shapes and cleans the content.

**Phase 2 — Mastering (server)**
The full preset chain. Produces a compliance-checked, level-matched, export-ready file. This is typically the final step and should be run on the complete, edited file.

**The natural order is: Edit → Master.** Users should not normalize or compress specific passages *after* mastering — doing so can break compliance. However, edge cases exist: a narrator may finish a file, get it mastered, and then need to add a few seconds of room tone or silence a small passage. These post-master touch-ups are level-neutral or near-neutral and should be supported without forcing a full re-master. The export UI should always display current compliance status (pass/fail) so the state of the file is self-evident — no lecturing, just clear signal.

## Architecture Overview

### Hybrid Client/Server Processing

Processing is split between client and server based on operation type. This is not a clean "everything server-side" model.

| Operation | Where | Rationale |
|---|---|---|
| Trim, cut, delete, silence, split | Client | Pure segment manipulation — no audio data touched |
| Normalize | Client | Linear operation, expected to feel instant. Quality gap vs. server is acceptable for spot work |
| Compression | Client | Interactive parameter tweaking expects immediacy. Two emulations — OptoSmooth (LA-2A opto) and FET Punch (1176 FET) — each a kernel run in an AudioWorklet for preview and in an OfflineAudioContext for apply, so the two are sample-identical. Both run their gain cell and saturator 4x oversampled (`src/audio/dsp/oversample.js`); detector and ballistics stay at base rate. Each reports 50 samples of latency, which the apply path compensates |
| Scheps Parallel | Client | A composite: two fitted Pultec stages around the existing OptoSmooth kernel, blended against a delay-compensated dry path. One worklet node, so the blend's alignment and the preview/apply equivalence are both structural rather than wiring the caller has to get right |
| Manual EQ and VoiceRx | Client | Two separate plugins, each a biquad cascade cheap enough to run live — the whole usability argument depends on hearing the change while moving the control. VoiceRx's analysis is a client port of Stage 3a — measurement-driven, so it needs no corpus, no reference curve and no preset |
| Noise reduction | Server (DeepFilterNet3) | Quality gap vs. RNNoise is significant and user-visible. Modal wait is normal for this operation |
| Full preset chain | Server | Always server-side |

**Why not route normalize and compress through the server too:** Users expect these to feel fast — a 10-second wait to normalize a 30-second selection would feel broken even with a progress modal. The quality delta between client-side and server-side normalize/compress is acceptable for spot editing. For Mode 1/2 users, the preset chain re-applies these operations at the end anyway with full compliance targeting.

**Why noise reduction must be server-side:** RNNoise (the client-side alternative) produces meaningfully worse results than DeepFilterNet3. For a product positioning on audio quality, shipping an inferior NR path for spot edits is not acceptable. The processing modal pattern normalizes the wait — every major audio tool works this way for NR.

### Full Preset Chain — Server Request Shape

```json
{
  "file": "<uploaded audio>",
  "preset": "acx_audiobook",
  "output_profile": "acx"
}
```

**Server response (preset chain):**
- Processed audio blob (WAV or MP3 per tier/preset)
- Processing report JSON (measurements, ACX certification if applicable, quality advisory flags)
- Waveform peak data JSON (~1000 points for canvas rendering)

The audio the user hears in-browser after mastering is **identical** to the download. There is no separate preview quality.

### Async Job Architecture

The server uses a job-based async model to avoid proxy timeouts on long-running operations (Cloudflare 524 at ~100s):

- `POST /api/process` returns `202 Accepted` immediately with a `jobId`
- Client polls `GET /api/jobs/:jobId` every 3 seconds until status is `complete` or `failed`
- `GET /api/jobs/:jobId/download` streams the processed file
- Jobs are held in-memory; they expire after 1 hour. A server restart loses in-progress jobs.
- Rate limit: 30 requests per 15-minute window per IP

**This is the only submission model for preset chain processing.** Do not add a synchronous path — even short files can take 30+ seconds once dereverberation and source separation are in the chain.

### Non-Destructive Editing Model

Original audio data is never modified until export. All edits are segment pointer manipulations (EDL model). Source buffers are immutable. Processing — both client-side and server-side — produces new buffers into the pool.

Key data structures: `Segment`, `SilenceSegment`, `Timeline` (ordered segment array), `EditorState`. See Wavely spec for full definitions.

## Preset + Output Profile Architecture

These are **independent** selections. A preset governs the character of processing. An output profile governs the loudness target, peak ceiling, and measurement method, and determines whether ACX certification runs.

### Presets (four at launch)

| Preset ID | Display Name | Audience | Channel Output |
|---|---|---|---|
| `acx_audiobook` | ACX Audiobook | Audiobook narrators | Mono |
| `podcast_ready` | Podcast Ready | Podcast hosts | Preserve original |
| `general_clean` | General Clean | Everyone else (default) | Preserve original |
| `noise_eraser` | Noise Eraser | Severely noisy recordings where standard processing has failed | Mono |

**Default preset:** `general_clean` — or `acx_audiobook` if the user has previously selected it.

### Output Profiles (three)

Output profiles are loudness targets, not compliance standards. They govern what the processing chain tries to achieve — they do not imply certification.

| Profile ID | Display Name | Normalization Target | Peak Ceiling | Measurement |
|---|---|---|---|---|
| `acx` | ACX Audiobook | -20 dBFS RMS | -3 dBFS | Unweighted RMS, full-file ungated (ACX standard) |
| `podcast` | Podcast / Streaming | -16 LUFS integrated | -1 dBFS | K-weighted LUFS (EBU R128) |
| `broadcast` | Broadcast | -23 LUFS integrated | -1 dBFS | K-weighted LUFS (EBU R128) |

### Default Pairings

| Preset | Default Output Profile |
|---|---|
| `acx_audiobook` | `acx` (locked) |
| `podcast_ready` | `podcast` |
| `general_clean` | `podcast` |
| `noise_eraser` | `podcast` |

**When output profile overrides preset:** the output profile wins on normalization target and peak ceiling. Example: `podcast_ready` + `acx` output profile → file processed with podcast character at ACX loudness levels.

**UI rule:** For `acx_audiobook`, hide/lock the output profile selector to `acx`. There is no meaningful reason to process an audiobook without targeting ACX levels, and surfacing the choice adds confusion.

**UI rule:** For `noise_eraser` with `acx` output profile, surface a warning: "ACX compliance is not recommended for Noise Eraser output. Separation artifacts may cause ACX human review rejection even if measurements pass."

## Processing Pipeline Architecture

The pipeline is **fully config-driven**. There is no hardcoded stage ordering. Each preset declares its own `stages` array in `src/audio/presets.js`, and the pipeline runner in `server/pipeline/index.js` executes those stages sequentially via a stage registry. This means:

- Adding or reordering stages for a preset is a data change in `presets.js` only — no changes to the runner
- Stages can carry inline config: `{ noiseReduce: { model: "rnnoise" } }` overrides that stage's defaults for that one call
- The same stage function can appear multiple times in a preset's chain (e.g. `noiseReduce` called twice with different models, `compression` called in multiple passes)
- Stage results accumulate in `ctx.results`; absent stages produce no orphaned keys in the report JSON
- There is no separate "Noise Eraser pipeline" — `noise_eraser` is a preset with its own `stages` array, executed by the same runner as every other preset

**Source of truth:** `src/audio/presets.js` — all preset and output profile definitions live here. The server re-exports from `server/presets.js`.

### Available Stages (stage registry in `server/pipeline/stages.js`)

**Pre-processing & measurement:** `decode`, `monoMixdown`, `measureBefore`, `measureAfter`, `peakNormalize`, `analyzeFramesRaw`, `remeasureFramesPostNr`

**Noise & tonal:** `humDetect`, `hpf`, `noiseReduce` (DF3 / RNNoise / DTLN switchable per call), `spectralSubtraction`, `clickRemove`, `dereverb`

**Voice enhancement:** `correctiveEQ`, `referenceEQ`, `airBoost`, `clipGainDeEss`, `deEss`, `resonanceSuppressor`, `breathReduce`, `vocalExpander`

**Dynamics:** `compress` (multi-pass, crest-factor driven), `parallelCompress`, `autoLevel`, `vadGate`

**Separation & extension (Noise Eraser):** `tonalPretreatment`, `separateVocals` (Demucs or ConvTasNet), `separationValidation`, `bandwidthExtension` (AP-BWE or LavaSR)

**ClearerVoice path:** `clearerVoiceEnhance` (mossformer2_48k or frcrn_16k)

**Special effects:** `harmonicExciter`, `vocalSaturation`, `roomPresence`

**Output & reporting:** `normalize`, `truePeakLimit`, `acxCertification`, `qualityAdvisory`, `encode`, `extractPeaks`, `roomTonePad`

### Key Processing Notes

**Frame analysis (`analyzeFramesRaw` / `remeasureFramesPostNr`):**
- Establishes the canonical noise floor measurement used by all downstream stages
- Runs multiple times per preset to refresh metrics after heavy processing passes
- Noise floor from this analysis drives silence exclusion thresholds, NR skip conditions, and ACX compliance checks

**Noise Reduction (`noiseReduce`):**
- Model is switchable per call: `df3` (DeepFilterNet3), `rnnoise`, or `dtln`
- `acx_audiobook` runs DF3 then RNNoise in sequence; `noise_eraser` runs DF3 before separation
- `skipBelowDb` option skips the call entirely if the measured noise floor is already below the given threshold
- **Never force a pass.** If noise floor can't reach -60 dBFS without artifact risk, report failure. Do not over-process.
- Noise floor enforcement only applies when `output_profile = acx`. For other profiles, reduction is applied for quality only.

**Compression (`compress`):**
- Crest-factor driven, not fixed-ratio. `targetCrestFactorDb` sets the target; the compressor adjusts ratio dynamically up to `maxRatio`.
- Most presets run 2–3 serial compression passes with decreasing target crest factors
- Followed by `parallelCompress` (wet/dry blend with VAD gate and integrated clip-gain de-esser)

**Vocal Expander (`vocalExpander`):**
- Frequency-selective silence-floor attenuator. Not a gate — soft-ratio, band-weighted, calibrated per file.
- Detection band: 80–800 Hz. Attenuation softened above 800 Hz via `highFreqDepth` to preserve consonants.
- Threshold set from post-compression silence P90 + headroom offset; skipped if already below -72 dBFS.
- Emits a `vocal_expander` key in the report; raises `over_expansion` advisory flag when it reaches into quiet speech.

**Auto Leveler (`autoLevel`):**
- VAD-gated gain riding — reduces level variance across voiced segments before final normalization.
- Must not run after `normalize` — gain riding post-normalization breaks compliance targets.

**Normalization & reporting:**
- `normalize`: `acx` output profile → ungated full-file unweighted RMS (FFmpeg `volumedetect`) — matches ACX's own measurement method. `podcast`/`broadcast` → K-weighted integrated LUFS (EBU R128) with pipeline silence exclusion (`noise_floor + 6 dB`) for elevated-room-tone recordings.
- `acxCertification`: runs for all presets when `output_profile = acx`. Six-point deterministic pass/fail. The `acx_certification` key is **absent** (not null) from the JSON for other output profiles.
- `qualityAdvisory`: runs for all presets and output profiles. Probabilistic flags (`info` / `review`), no aggregate score, each with a "Mark as reviewed" checkbox.

See `docs/instant_polish_compliance_model_v2.md` for full flag definitions, JSON structure, and UI model.

### Preset Character Distinctions (do not converge)

- **ACX Audiobook:** Clean, transparent, controlled dynamics. Highest priority on noise reduction quality and artifact-free output. Conservative compression. Dual NR pass (DF3 → RNNoise).
- **Podcast Ready:** Punchy, intimate, compressed. More aggressive EQ. LUFS target (not RMS). Stereo preserved for dual-host. Vocal saturation + room presence added for character.
- **General Clean:** Pragmatic. Uses ClearerVoice enhancement for broad-band cleanup. More aggressive de-esser. No strong tonal character.
- **Noise Eraser:** Voice extraction, not noise reduction. Prioritizes noise removal over voice transparency. Uses Demucs source separation. Output may have a "dry booth" quality.

## ACX Certification and Quality Advisory — Key Rules

**ACX certification is the only formal certification standard.** Podcast and broadcast loudness targets are norms, not standards. Streaming platforms normalize on playback — there is no external body to certify against. Do not present pass/fail framing for `podcast` or `broadcast` output profiles.

**The tool certifies technical compliance. It does not certify ACX acceptance.** ACX also applies a human quality review. The quality advisory flag system addresses this separately.

**Advisory flags are not failures.** A technically certified file with advisory flags is valid and submittable. Flags inform the user's review decision — they do not gate the download or export.

Full specification: `docs/instant_polish_compliance_model_v2.md`.

## ACX-Specific Features

These apply only to the `acx_audiobook` preset:

- **Room tone padding:** Stage `roomTonePad` is implemented and available in the stage registry — auto-detect and pad head (0.75 s) and tail (2 s) using actual room tone from the file's quietest silence segment. Not digital silence. Currently not included in the `acx_audiobook` stages array.
- **ACX compliance report:** ✓ Implemented — Per-file six-point technical certification + quality advisory flags. `acxCertification` runs for all presets when `output_profile = acx`.
- **Plosive and breath detection:** ✓ Implemented — Surfaces as quality advisory flags for manual review before ACX submission.
- **Batch processing (Creator tier gate):** ✗ Not yet implemented — Multi-phase: batch analysis → per-file processing → cross-chapter consistency pass. Consistency pass aligns RMS (< 1 dB deviation from batch median) and spectral centroid (< 15% deviation) across chapters. This is the **primary value prop for narrators**. Planned for Sprint 5.

**The cross-chapter consistency problem is the highest-value unsolved pain in ACX narration.** Single-file tools don't address it. Instant Polish batch mode will. This is not yet built.

## Implementation Status

### Complete (as of May 2026)

**Frontend:**
- Vue 3 (Composition API) production app — not a PoC
- Non-destructive timeline editor: trim, cut, delete, silence, split, fade, volume, copy/paste
- Undo/redo stack (50-item cap). **Each entry carries the name of the operation that created it**, and undo/redo announce it ("Undid cut", "Redid normalization") on the same toast every edit already uses — undo was the one step in the loop with no feedback, so the only way to tell a no-op undo from a working one was to look at the waveform. The label travels with the state onto the redo stack, so redo names the same operation. Unlabelled entries fall back to a bare "Undone" rather than inventing a name. **The label is used verbatim and is therefore authored in reading form** — lower case for ordinary operations, its own case for anything opening with a name ("VoiceRx", "Scheps Parallel"). A rule deriving that from the label shipped first and was wrong on three of nine real labels ("voiceRx", "airBoost", "scheps Parallel"); it cannot be made right, because "Scheps" and "Silence" are the same shape. Pinned in `test/ui/undoHistory.test.js`.
- **Save / Save As write the file back to disk, and the first Save is always a Save As.** Edits used to exist only until an export, so the loop had no "keep what I have and carry on" step. `Save` (Ctrl+S) renders the timeline and writes it over a destination the user has already named, via the File System Access API; `Save As` (Ctrl+Shift+S) picks that destination. **A handle is only ever taken from a *save* picker, never from an open picker or a drop** — this app encodes 16-bit WAV only, so a Ctrl+S that silently inherited the source file's handle would overwrite a 24-bit master with a reduced-depth render of itself. That is why the first Save on any document prompts, whatever route the file arrived by. Handles are also deliberately **not** persisted to IndexedDB: a document does not survive a reload (buffers are in memory), so a restored write target would have nothing left to write.
- **Dirtiness is a revision comparison, not "has any undo history".** The old test (`undo.length > 0`) could only ever go one way, so a file stayed "edited" forever and the close guard nagged about work already on disk. Each document carries a `revision`, bumped on every mutation, and a `savedRevision`; **the revision travels on each history entry**, so undoing back to the state that was last saved reports clean again and redoing re-dirties. Stack depth cannot do that — the 50-entry cap shifts the bottom off. Same predicate drives the tab marker, the Save button's dot, the close confirmation and the `beforeunload` guard, so the four cannot disagree. Pinned in `test/ui/fileSave.test.js`.
- **Where there is no write API (Firefox, Safari), Save falls back to a download** — same bytes through the same render, just via the download folder. A dead button on two of three browsers is worse than an inelegant one.
- Waveform visualization (Canvas 2D, peak caching, device pixel ratio support)
- **A selection needs 4 px of travel before it exists.** Reported as accidental selections from ordinary clicks in the waveform, and the cause is that a click is never perfectly still — a couple of pixels between mousedown and mouseup was enough to leave a sliver of selection behind, and everything downstream then acts on the sliver: Space plays it instead of the file, the effect windows apply to it, and the trim operations light up. The threshold latches, so dragging out a selection and pulling back to a two-pixel one is still a selection; only the opening move decides. `SELECTION_DRAG_THRESHOLD_PX` in `WaveformArea.vue`.
- **A selection's edges are draggable.** A selection that can only be made in one gesture has to be remade from scratch every time it lands a few pixels off, which at any working zoom is most times. Grabbing an edge within 6 px anchors the drag on the *opposite* edge, so from mousedown on the gesture is identical to making a selection — including dragging one edge clean past the other, which `setSelection` normalises rather than inverting. Two deliberate differences from the create gesture: **the 4 px threshold does not apply** (there is no sliver to protect against when the selection already exists, and a 3 px nudge of a boundary is the common case), and **the playhead does not move** — trimming a boundary is not seeking. The cursor turns to `ew-resize` on hover, because a hit target with nothing to say it is one is discoverable only by accident. When both edges are inside the hit radius — a short selection, or a zoomed-out one — the nearer wins, ties to the end. Geometry is in `src/audio/selectionDrag.js` rather than the component so the numbers that decide the feel can be tested without a canvas; pinned in `test/ui/selectionDrag.test.js`.
- Playback with A/B before/after comparison
- **Looping is scheduled on the audio clock, not restarted from an animation frame.** Reported as latency when a loop restarts, and it was: the frame that noticed the end fired up to one refresh interval *after* it, then started nodes at `currentTime`, which the render quantum rounds up again. Measured against a frame-stepped fake context, the old path put **8.4–15.4 ms of silence (mean 13.0) at every seam** — and that is a floor, since it models neither the quantum nor real rAF jitter. The next pass is now booked 150 ms ahead at the exact context time the current one ends, so the seam is sample-accurate by construction and the animation frame only moves the playhead. `test/ui/playbackLoop.test.js` measures the gap from the scheduled start times rather than leaving it to the ear — the seam is the kind of defect that is obvious in a room and invisible on a stopwatch, which is why it went unmeasured.
  - **A repeat starts at the loop region, not where the first pass started.** Playing a whole file from the middle loops back to the top; playing a selection loops the selection. That was the old behaviour too and it is easy to lose when the restart moves into the engine.
  - **Moving the selection moves the loop, live.** Reported from use: dragging a selection edge under a running loop kept looping the old region until playback was restarted, which makes auditioning a boundary by ear a stop/adjust/start cycle per attempt — most of what the draggable edges are for. `setPlaybackRegion` re-scopes the sounding transport against the same audio clock the seam uses, so a region change is no more of a gap than a repeat is: **an end moved later schedules only the tail past the old end, joined at the old end's context time**; an end moved earlier stops the sounding nodes at the new end instead of the old; a repeat already booked into the lookahead window is cancelled and rebooked against the new region. A moved *start* needs none of that — it is where the next repeat begins, so it lands at the seam like any other loop bookkeeping. **One case jumps, and only one**: an end dragged behind the play position leaves nothing of the pass to play out, so a looping transport wraps immediately and a non-looping one ends — the alternative is playing audio the user has just excluded. A drag is a stream of these calls rather than one, so the shrink-then-extend path is pinned too: each shrink stops the sounding node early, and the extension has to pick up at exactly that instant or the drag leaves a hole mid-region. **Clearing the selection is deliberately not a region change** — it happens on every click in the waveform, and re-scoping playback on a stray click is worse than letting the loop run on.
  - **The de-esser's envelope needed `stopTransport(when)` to make this work.** It stopped its modulator immediately, so booking the next pass ahead of the seam would have cut the tail off the pass still sounding. It now stops the outgoing one *at* the seam, with the `onended` handler guarded on node identity so the outgoing one cannot clear `running` for the pass that replaced it. Its meter is re-anchored on a shorter 60 ms lead for the same reason — re-anchoring points the meter at a pass that has not started, and that window is kept under two animation frames.
- Preset panel (4 presets) + output profile panel (3 profiles) with dynamic UI rules
- Processing report panel (measurements, ACX certification, advisory flags)
- **OptoSmooth's R37 emphasis was modelled backwards, and the reason it survived is that it had no test.** It was built as a high SHELF BOOST from unity — +8 dB above 2 kHz, lows left at full level. On the hardware R37 is a trimmer in a PASSIVE network, and a passive network cannot boost: "emphasis" is achieved by discarding lows and letting the side-chain amp make the level back. Now a shelving **attenuation of up to 10 dB below 1 kHz**, unity above it.
  - **The consequence was not cosmetic, and the direction was wrong too.** Peak Reduction is side-chain gain into a FIXED internal threshold, so a model that adds gain at the top adds compression where the hardware removes it. Measured on a 120 Hz plosive at Peak Reduction 65: the old model moved gain reduction **13.61 → 13.67 dB** across the entire sweep — 0.06 dB, upward. The new one moves it **13.61 → 6.35 dB**, downward and monotonic. The control now has authority over the one thing it exists to reject.
  - **THE KNOB ALSO RAN THE WRONG WAY, and that is a separate fix.** The parameter is now `r37`, 0–100 read as knob rotation, matching the manual: *"factory set for a 'flat' side-chain response (clockwise). Increasing the resistance … by turning it counter clockwise will result in compression which is increasingly more sensitive to the higher frequencies."* So **100 is fully clockwise, flat, factory, and the default**; winding down to 0 filters. The old `emphasis` ran 0 = flat, which inverted both the hardware and every reference plugin — the same number meant opposite things in our panel and in anything it was compared against, which is exactly how an A/B gets run at two different settings without anyone noticing. Scheps pins `r37: 0`.
  - **The stock position is bit-identical to before the mechanism fix**, so nothing using the default moved. Only off-flat settings changed, and every one of them now compresses less at a given Peak Reduction.
  - **`test/dsp/la2aSidechain.test.js` is the guard that was missing.** Five behavioural assertions — flat at the factory position, monotonic LF rejection, HF drive left alone, side-chain attenuated rather than boosted, 80 Hz HPF always in circuit. **Three of the five fail against the old model**, which is the property that makes them worth having; a control with no test is how a backwards one shipped unnoticed — twice, once in mechanism and once in direction.
  - **Still unmeasured: the 1 kHz corner and the 10 dB depth.** Both come from secondary sources describing the hardware, not from a swept measurement of a real unit — the same standard the Pultec curves were held to, and not yet met here.
  - **THE REFERENCE EMULATION CANNOT SUPPLY THEM — measured, and it is not a near miss.** Analog Obsession's LAEA has no emphasis control at all; the unlabelled knob taken for one is a mix control, and its `HPF` toggle is a **2-pole Butterworth at 84.5 Hz** (fitted to 0.05 dB rms over 63–400 Hz; order is well determined, a 1-pole fit costs 0.89 dB). That is a utility rumble filter, not R37: it measures **−6.3 dB at 63 Hz, −1.7 at 100, −0.3 at 160, and exactly 0.00 at 250 Hz and above**, where R37 wound fully counter-clockwise must still be taking **6.7 dB out at 400 Hz**. The 0.00 dB readings settle it without any modelling assumption in the way. Fitting our shelf to this toggle would have calibrated one control against a different control and recorded the result as measured.
  - **The same capture retroactively validated the taper fit's premise, which is the useful half.** With HPF off, LAEA's gain reduction is **10.39 dB at every tone from 63 Hz to 3.15 kHz, ±0.01** — its side-chain has no frequency shaping whatsoever in that range. The eight taper captures were therefore taken through a genuinely flat side-chain, which is the condition that fit assumed and could not previously check.
  - **The probe floor was 63 Hz, so our own always-on 80 Hz side-chain high-pass is still untested.** It only does real work below that (−0.7 dB at 63, −3.4 at 40), and no tone in the set reaches it. A probe designed to answer one question did not answer the adjacent one — add 31.5 and 40 Hz next time.
- **AUTO MAKEUP IS PEAK-REFERENCED ON BOTH COMPRESSORS, and matching RMS was the bug.** `computeAutoMakeupDb` / `computeFET1176AutoMakeupDb` restored the *average* level, which returns only the average loss and therefore leaves the output exactly as loud as the input — a compressor that by construction cannot make anything louder. Makeup has always meant giving back what was taken off the peaks: the loud moments land where they started and everything underneath rises with them. **The guarantee that buys is the important half — the output can never come out hotter than the source at any setting**, which is what stops a surviving transient reading as an errant peak.
  - **True peak, not a percentile, and that was measured.** A percentile of short-block peaks looks more robust and is worse where it counts: on real speech a fast transient survives compression nearly intact while the p99 comes down several dB, so percentile-referenced makeup over-compensates and pushes that survivor **up to 5.5 dB ABOVE the source**. True peak cannot do that. The cost is the opposite failure — one uncompressed click sets the reference and the makeup comes out small — which is the safe direction.
  - **The same rule reads very differently on the two units, and `test/dsp/compressorMakeup.test.js` pins both.** FET Punch catches peaks, so restoring them lifts everything underneath: **+1.1 to +2.2 dB** of average gain. OptoSmooth on fast material does the reverse — a 10 ms attack lets onsets through while the body is pulled down, so it reduces the average MORE than the peaks and peak-referenced makeup comes out **quieter on average**. That is an opto leveller being itself: reach for FET Punch to make something louder, OptoSmooth to make it steadier. On slower material the Opto does earn density — **+1.6 dB** measured on a real narration clip at Peak Reduction 60.
  - **The Gain/Output knob is draggable while AUTO is lit, and touching it takes over.** Discarding the drag is what shipped, and it reads as a broken knob: an "OptoSmooth at 75 with no makeup gain" comparison turned out to carry **9.45 dB**, because setting the knob to 0 never took and nothing said so.
- **THE OPTO'S PEAK REDUCTION TAPER IS NOW FITTED TO A REFERENCE LA-2A, and it was wrong in two independent directions at once.** Eight captures of one narration clip through Analog Obsession's LAEA at knobs 20/30/40/56/70/80/90/100 (its +1.34 dB insertion gain removed). - **Scheps Parallel** — Andrew Scheps' Pultec/LA-2A vocal trick as one plugin. Pultec push → OptoSmooth → Pultec recovery on a wet path, blended against the dry. **Four visible controls** (Character, Squash, Mix, Output) because the trick's defining settings are not choices: the LA-2A's R37 emphasis is pinned wide open (that *is* the trick — the side-chain filtered so the cell stops ducking on plosives and rides the presence band instead), mode is COMP, and its makeup stays at 0 so the tube stage isn't driven by gain that belongs after the post EQ.

Measured cost of the old staging was small — about **1 dB less harmonic content** (−45.6 vs −44.5 dBc on a 200 Hz tone), with levels moving by hundredths of a dB, because gain commutes exactly through a linear biquad cascade. **The reason it was worth fixing is structural rather than sonic**: the makeup now flows through the compressor's own machinery, so changes to how OptoSmooth computes makeup reach this plugin instead of having to be mirrored into it. The dry side runs a delay line of exactly that latency, and the plugin reports it once for the offline apply path to trim. Verified: at Mix 0 the output is the input, sample for sample.

  - **THE MAKEUP IS REFERENCED TO THE LOUD PARTS, NOT THE AVERAGE — matching the average is a compressor that cannot make anything louder.** That is what makeup gain has always meant: the compressor pulls the loud moments down, you hand back what it took, the loud parts land where they started and everything underneath comes up. It is not the several dB the textbook picture suggests because **a 10 ms attack lets syllable onsets through nearly intact while the cell pulls the sustained body down**, so the chain reduces the average almost as much as it reduces the peaks: at Squash 80 average GR is 4.28 dB while restoring the average costs 3.54, only ~0.6 dB of daylight. - **The Soft Clipper reports a RESIDUAL, and it is the readout the other two cannot stand in for.** The lamp says how deep, ENGAGED says how often, and a setting can hold both steady while doubling the damage — measured across HF Emphasis on real narration, peak reduction moves 0.1 dB while the residual moves 2.5. It is the number behind the DELTA button: what that mode auditions, this reports. **In dBc**, residual energy against dry energy, so it is invariant to how loud the file is and to Output Trim (a gain match for A/B has no business moving a diagnostic), and it is the unit this stage's measurements were already recorded in.
  - **Measured where the delay-aligned dry signal already exists** — the same line DELTA uses, and the only point in the kernel where a dry and a finished wet sample sit together. Anywhere else compares the oversampler's group delay against itself. It costs one multiply-add per sample.
  - **TWO SMOOTHED ENERGIES, ONE DIVISION — smoothing the RATIO is a different measurement and it shipped first.** A per-block ratio is large wherever dry is small, so its running mean is dominated by the quietest voiced blocks, which carry almost none of the distortion. Against a whole-file energy ratio across HFE 0 → 12 it reported a **minimum at 5–6 on a file whose residual actually falls monotonically to 12**, and compressed a real 2.4 dB span to 0.4. Two energies reproduce the whole-file figure to a constant per-file offset (−0.8 / −1.0 / +0.8 dB on three narrators, the gating difference), so comparisons within a file are exact and the shape is right on all three.
  - **⚠ ITS FLOOR IS THE OVERSAMPLER, NOT ZERO.** The residual runs from the RAW input to the finished output, so it contains everything the stage does — including the oversampler's reconstruction error, present whether or not the curve fires. Measured fully bypassed: **−70.7 dBc on speech, identical at every input level and every emphasis setting**, which is what a linear error looks like. That is 25–40 dB below the range this stage produces in use (−30 to −45 dBc on three real narrators), so it cannot affect a comparison between settings — but a reading near −70 means "the oversampler and nothing else", not "clean".
  - **Gated and windowed exactly like ENGAGED** (voiced blocks, 2 s) so the two figures beside each other describe the same stretch of audio. Energy is averaged and then converted, never the reverse — a mean of dB is a geometric mean of powers, which on a quantity that is zero for most blocks reads far below the true ratio.
  - **What it is for, and the open question.** Real narration puts the residual minimum partway up the HF Emphasis knob on some material (**HFE 5** on a raw file, **3** on a hard-mastered one) and monotonically at the top on others — a U-curve from two competing terms, low-frequency distortion falling as the compensation raises the threshold while high-frequency distortion rises as more fricatives are caught. Listening independently preferred HFE 3–5. **Whether the measured minimum is the setting that sounds best is not established**, and it is the question that decides whether an automatic version is worth building: this stage already has one recorded case — the KNEE shapes — where 9.2 dB LESS residual energy sounded MORE conspicuous, because sparse distortion is more noticeable per unit energy than continuous distortion.
- **The Soft Clipper can generate EVEN harmonics now, and before this it generated exactly none.** The curve is odd symmetric — one of the five guarantees at `MAX_REDUCTION_DB` — and an odd curve produces odd harmonics and nothing else. Measured: on a 220 Hz tone 6 dB over threshold **H2 sits at −144.3 dB**, and on three real narrators the even-order energy is **exactly zero**, using the decomposition `F_even(x) = (F(x) + F(−x))/2`, which returns a buffer of zeros to the last bit. Odd harmonics are the buzz and fizz this file already documents; the warmth people describe as tube or tape is second and fourth order, and **no setting of this stage could reach any of it.**
  - **`asymmetry` (0–100) is a DC offset before the shaper, scaled to the threshold.** On the same tone at 6 dB over: H2 goes **−144.3 → −38.8 → −26.8 → −22.2 dB** across asym 0 / 0.05 / 0.20 / 0.35, overtaking H3 at the top — the classic tube signature.   - **Everything is ABSENT at 0, not flat.** The offset and the DC blocker are both bypassed, so the shipped patch is bit-identical to the build before this existed — the same rule the emphasis pair follows, and the thing that buys the right to put a colouring control inside a stage whose identity is transparency.
  - **⚠ THE DC BLOCKER WAS NEARLY DROPPED ON A ONE-OPERATING-POINT MEASUREMENT.** At the default the DC is 70–90 dB below peak and looks like nothing. Under drive it is a different quantity: with the threshold 30 dB down and no blocker, a 120 Hz tone leaves **−45.2 dBFS** of DC and an input that *already carries DC* comes out **5.1 dB below its own peak** — which shifts the waveform bodily and corrupts the peak measurement ACX is built on. `DC_BLOCK_HZ = 2`: rejection is total at any corner, so the corner only trades settling against disturbance, and 2 Hz leaves −123.5 dBFS in 0.04 s while costing **−35.1 dBc against −29.9 at 5 Hz and −17.2 at 20**.

  - **THE SIGN IS CHOSEN BY MEASURING THE WAVEFORM'S OWN LEAN.** Even content is *identical* for ±offset (−37.4 dBc either way on all three files), so the sign buys none of the warmth — what it changes is how much *other* distortion is paid for it, and that tracks the material's skew. Speech is asymmetric by nature and the polarity depends on the speaker, the mic and any flip in the chain, so it cannot be assumed. The offset now leans **against** the skew, tracked in real time from a third moment of the pre-emphasised downmix (`SKEW_TAU_S`) — a property of the *input*, like the speech level, so unlike the HFE auto-setter it needs no counterfactual outputs. Measured at asymmetry 60: the file with skew **+0.65 goes −31.75 → −35.01 dBc** of total distortion, and the two negative-skew files are unchanged because positive was already right for them.
  - **⚠ SCALING THE MAGNITUDE BY THE SKEW SILENTLY TURNS THE KNOB OFF.** The first version used `direction = -tanh(skew / scale)`, which reads as an elegant continuous sign and commits properly on real material — and gives *zero* offset on symmetric material, so the control does nothing at any setting. Caught by even-order energy going to exactly zero on synthetic probes, which are sums of sines and symmetric to the last bit. **Only the sign comes from the skew; the magnitude is the feature and must not depend on the material.**
  - **⚠ THE ESTIMATE IS LARGE AND WRONG EARLY ON, AND THE DECISION IS STICKY, so one early excursion latches for the whole file.** On a probe whose settled skew is 0.002 the running estimate reads **1.15 at 0.5 s, 0.27 at 1.0, 0.12 at 1.5, 0.011 at 4.0** — off by three orders of magnitude at half a second. That is estimator variance, not bias: a ratio of two one-pole averages of x² and x³ over half a second of syllables says almost nothing. The first build decided at the speech tracker's 500 ms warm-up and latched the **wrong sign on symmetric material**. The decision now waits a full time constant of gated evidence and holds the shipped default until it has it, so the opening of a file is never worse than before.
  - **A polarity-flipped recording is now processed identically**, since flipping the input flips its skew and therefore the chosen offset. Good in itself — mic polarity is arbitrary. ⚠ It also means the `F_even = (F(x) + F(−x))/2` decomposition **cannot** measure even content on skewed material any more: the negated run is not the same processing. The even-harmonic tests use symmetric probes, where the deadband holds the sign still, for exactly that reason.
- **The Soft Clipper's HF LOSS is not gap loss, and getting that wrong would have cost the stage a guarantee.** Gap loss is the reproduce head averaging flux across a finite gap — `sinc(π·g/λ)`, a function of gap width, tape speed and frequency and **not of level**. Modelled faithfully it is an always-on shelf, which colours every sample of every file and costs "unity below T" outright. What actually makes tape lose top end when pushed is **short-wavelength self-erasure**, which is strongly level-dependent — and that is the version worth having, because a colour that vanishes with level leaves quiet material bit-exact.
  - **Measured: exactly 0.00 dB at every frequency at and below the threshold, at full knob.** Above it the shelf arrives — at −2 dBFS into a −14 dBFS threshold, isolated by subtracting the same measurement with the knob at zero, it runs **0.00 / −0.17 / −1.62 / −2.87 / −3.64 dB** at 100 Hz / 1k / 4k / 8k / 16k. Driven by level *relative to the threshold*, so it is level-invariant like everything else here.
  - **THE STRUCTURE IS A BLEND, NOT A RECOMPUTED FILTER**: `out = g·x + (1−g)·lowpass(x)`, one fixed one-pole and a per-sample `g`. That is exactly a first-order high shelf — unity at DC, plateauing at `g` above the corner — with two properties a moving biquad would not have. It is **exactly** transparent at `g = 1`, so the bypass is free rather than approximate. And it **provably cannot boost**: `|g + (1−g)·LP| ≤ g + (1−g)·|LP| ≤ 1` for any `0 ≤ g ≤ 1`, since a one-pole lowpass has magnitude at most 1 everywhere. "Never boosts" survives by construction, which matters for a filter whose depth moves per sample.
  - Mutations caught: making the shelf static (i.e. modelling gap loss properly) and blending the wrong way round.

- **LOOKAHEAD LIMITER — the gain-reduction module behind it** (`src/audio/dsp/lookaheadLimiter.js`). The soft clipper takes peaks down by reshaping samples, which generates genuine in-band harmonics (−16 dBc at 13 dB of drive, and 8× oversampling changes it by nothing). A lookahead limiter takes the same peaks down with a smooth **gain envelope**, so its error is intermodulation and slight pumping rather than a harmonic series on top of the voice. The intent is that the limiter does the bulk of the peak control and the curve catches what slips past.
  - **THE NO-OVERSHOOT GUARANTEE IS STRUCTURAL, and the construction exists for it.** `gReq = min(1, T/|x|)`; `gMin` = centred running min over `[n−L, n+L]`; `g` = triangular smoother of `gMin` with **the same support**. Then `g[n] ≤ gReq[n]` always, in one line: `g[n]` is a convex combination of `gMin[k]` for `k` within L of n, and every such `gMin[k]` is a min over a window that *contains* n. ⚠ **Widen the smoother past the min window and the guarantee is gone** — that is the mutation, and it is caught. Latency is 2L; O(1) per sample via a monotonic deque and two running-sum boxcars.
  - **⚠ A CIRCULAR DELAY READ-BEFORE-WRITE DELAYS BY ITS LENGTH, and sizing it `2L+1` instead of `2L` put the envelope one sample off the peak it was computed for.** On a bare impulse that is the entire error: measured, it overshot the threshold by 0.2% — small enough to read as float noise, large enough to void the guarantee. Found by an adversarial test rather than by inspection.
  - **⚠ IT IS NOT UNITY BELOW T, AND AN EARLIER TEST NAME CLAIMED IT WAS.** The curve is unity below the threshold sample by sample; the limiter's envelope is smoothed over ±L, so anything within L of a crossing is ducked whether or not it is itself over T. Measured on three narrators at a −14 dBFS threshold with 2 ms of lookahead: **24–36% of the sub-threshold samples are gain-reduced, by 2.2–5.4 dB on average and up to 13 dB**. Reported by ear as a tonal change below the threshold, and that reading was right. It is not a defect — it is what a smooth gain envelope does, and it is the limiter's central difference from the curve. The test is renamed to what it actually pins (a signal that NEVER crosses is a pure delay) and the ducking now has its own assertion.
  - **⚠ LENGTHENING THE LOOKAHEAD MAKES IT WORSE, so the two knobs pull against each other.** 2 ms → 5 ms takes the ducked share from 31.2% to 36.1% on the reference narrator. But a window shorter than a cycle is its own problem: on a tone 3 dB over the threshold, 80 Hz measures **−39.2 dBc at 2 ms and −151 at 5 ms** — at 2 ms the gain follows the waveform rather than its envelope, which is harmonic distortion of the bass rather than gain riding. Clean from 200 Hz up at either. Both are pinned.

It is the right number for "did moving work onto the limiter reduce harmonic distortion" and the wrong one for "which sounds better" — the limiter's own error is intermodulation and gain movement, which this does not count. The ear decides.

  - **BAND-SPLIT LIMITER — built, measured, NOT wired to a parameter** (`src/audio/dsp/bandSplitLimiter.js`). The broadband envelope's one measured cost is that it ducks 24–36% of sub-threshold samples, because a voice's peaks are overwhelmingly low-frequency and a single envelope hands a plosive's gain reduction to the sibilants as well. Splitting first and giving each band its own envelope confines the ducking to the band that caused it.   - **⚠ THE OBVIOUS CONTROL IS THE WRONG ONE, and it briefly said the opposite.** Comparing the split at ceiling factor c against a broadband limiter at the SAME c is not a matched comparison — the split's guaranteed sum bound is N times its per-band ceiling, so the same c is a far tighter ceiling for the broadband path. Soften moves the top end and the residual; hysteresis moves neither, and costs the same ~0.8 dB of residual whether Soften is engaged or not. They are separately reasonable-about: **Hysteresis decides how eager the curve is after a loud moment (threshold, control path); Soften decides how sharp an edge is allowed to reach it (audio path).**
  - **A mutation that survived four assertions: inverting the knob's mapping.** Every HF test still passed, because the tone probe sits 19 dB over the threshold where the limit binds even at scale 1 — Bernstein's promise covers material at or below T only. Monotonicity across the knob is what catches it, and is now its own assertion.
- **A LEVEL-DEPENDENT RATE LIMIT — REAL TAPE-STYLE TRANSIENT SOFTENING — MEASURES AS EXACTLY NOTHING ON SPEECH WHILE IT RESPECTS TRANSPARENCY, and the reason is structural rather than a tuning failure.** Prototyped in the oversampled path both before and after the curve: allowed slope `S = (π/OVERSAMPLE_FACTOR)·T·factor`, with `factor` shrinking as the limiter's own output rises above `T`. The reference is **Bernstein's bound** — a signal bandlimited to the base rate's Nyquist and bounded by `T` cannot move more than `2πB/fs_os·T` per oversampled sample — which makes "unity below T" exact rather than approximate, and it verified **bit-identical** on quiet material at full knob.
  - **It works, and speech never triggers it.** On a loud 8 kHz burst it bites hard (peak 0.406 → 0.173). On 35 s of real narration, at every peak target and both positions and every knob setting, the output is **identical to the last decimal** — residual −33.90 dBc at −3 dBFS out whether the limiter is at 0 or 100.
  - **THE NUMBER THAT EXPLAINS IT, measured on the signal the curve actually sees (post-emphasis, oversampled) across EVERY sample rather than only the peaks.** Slope/T at HF Emphasis 0: p50 0.0014, p99 0.031, p99.99 0.096, **max 0.157**. At HFE 6: p50 0.0016, p99 0.045, **max 0.273**. The transparency bound is **0.785**. So the single fastest instant anywhere in the file — sibilants and plosive bursts included — is **2.9× under** the slowest limit that keeps "unity below T" exact.
  - **⚠ AN EARLIER NOTE HERE SAID "A VOICE DOES NOT HAVE FAST HF TRANSIENTS". THAT IS WRONG AND WAS CHALLENGED.** A voice obviously has fricatives and plosive bursts. Two things were also wrong with the measurement behind it: it was taken on the RAW signal rather than the emphasised one the curve sees, and it was gated to samples already above the threshold, so it could only ever have described the low-frequency peaks. The corrected figures above are ungated and measured in the right place — and they say the same thing for a different reason. **"Fast" here is set by the sample rate, not by speech**: the bound has to accommodate a full-amplitude sine at the base rate's Nyquist, so it is enormous compared with anything a voice does at a level near the threshold. The right statement is that nothing in this file moves fast enough RELATIVE TO T, not that the voice lacks HF.
  - **What that closes off.** Rate limiting cannot contribute to peak control on voice without abandoning bit-transparency below the threshold, and abandoning it buys a lowpass, not peak control. It also retroactively explains why the "hysteresis" here became a threshold modulator: the rate mechanism has nothing to grab on this material. ⚠ **This does not generalise past voice** — on drums or full-band music the slope distribution is entirely different and the same code could matter a great deal.
- **⚠ THE SOFT CLIPPER'S "HYSTERESIS" IS NOT TAPE HYSTERESIS, AND THE NAME INVITES THE WRONG READING.** It is a control-path term: a memory of recent drive that lowers `T`, the threshold the waveshaper reads. It never touches a sample. What people mean by tape hysteresis is a memory inside the **transfer function** — the medium not fully following a fast enough change, so a transient returns lower and with its slope rounded while a slow excursion of the same amplitude passes intact. Ours does neither: the curve reacts instantly given `T`, and the memory makes it react **more** to the next transient rather than less. Measured, it also **concentrates** distortion on onsets (residual 21 dB hotter there than on sustained speech, widening 1.3 dB across the knob) rather than spreading it.
  - **BEFORE OR AFTER THE WAVESHAPER IS NOT A REAL CHOICE HERE, and that is provable rather than arguable.** The curve is level-invariant, so `softClip(x, T/g) = (1/g)·softClip(g·x, T)`: lowering the threshold by g dB IS raising the drive by g dB into a fixed threshold and taking g dB back off after. Built both in the kernel and rendered 35 s of real narration — they differ on **373 of 1.7M samples, worst −144.5 dBFS**, which is float rounding. Applying the memory *after* the curve instead is a different and worse thing: a slow level ride that lowers output peak and RMS together (−3.53/−21.78 against −3.49/−21.71) and adds no shaping, so it subtracts from peak control rather than adding to it.
  - **⚠ A NAIVE SLEW LIMIT IS NOT THE ANSWER, AND THE PROBE THAT SAID SO WAS UNFAIR.** Matched on output peak, a global slew limit measures **−8.27 dBc against the clipper's −33.90** — 25 dB worse — with >2 kHz residual at −15.53 dBc and output RMS down 0.4 dB. But an always-on slew limit slews everything, so it is a heavy lowpass whose "residual" is mostly *removed program content*, not added harmonics, and the dBc metric cannot tell those apart. The fair test is a **level-dependent** rate limit — engaged only above the threshold, which is what makes tape's version level-dependent too — and it has not been run.
- **How it works, and why the threshold is what moves.** It is a short-term memory of recent drive — the "lite" version the tape architecture asked for, a one-pole lag rather than a Jiles-Atherton model, and it should be described as a memory effect rather than as a simulation of magnetisation. The obvious alternatives are to modulate the drive into the curve or the knee, and **both reshape the curve**, which puts the monotonicity guarantee back in play on a curve already spending 0.717 of its slope budget at LATE. Moving `T` **translates** the curve without changing its shape, and a translated monotonic curve is monotonic — the guarantee survives by construction rather than by measurement.
  - **⚠ "A LOUDER INPUT ALWAYS PRODUCES A LOUDER OUTPUT" DOES NOT SURVIVE, and should not be claimed.** That is a statement about a memoryless curve; no state-dependent gain can keep it, which is true of every compressor in this app and is what nobody calls a fold. The property that actually prevents the destructive sound is **no instantaneous fold** — at any frozen state the transfer curve is monotonic. That is what translating `T` guarantees and what the tests check.
  - **⚠ IT SHIPPED FIRST WITH A SEPARATE 80 ms RELEASE AND THE RELEASE DID NOTHING.** The comment credited the loop to asymmetric ballistics; measured, that was wrong. Swept 5 / 80 / 150 / 300 / 600 / 1200 ms against a fixed 5 ms attack, loop width is **identical to three decimals at every value** — 1.881 dB on a 100 ms ramp, 1.508 on a 500 ms one — and symmetric 5/5 reproduces 5/80 exactly. A one-pole chasing a signal that has already been through the detector's own **1 ms / 150 ms** follower just tracks it. **The asymmetry that makes the loop comes from upstream, not from this stage**, so there is one time constant here now rather than two. A constant that cannot move any measurement is not a tuning.
  - **The loop is real and the knob widens it: 0.61 → 1.31 → 1.88 dB** across hysteresis 0 / 50 / 100 on a 100 ms ramp, narrowing to 0.65 at full on a 2 s one — it needs the level to be moving faster than the state can follow. **The baseline is not zero**, for the same reason: the detector's follower is already asymmetric, so the stage always had a little of this and the knob deepens an effect rather than introducing one.
  - **`HYST_TAU_MS = 5` is a choice, not a fit** — loop width at hysteresis 100 runs 1.570 / 1.881 / 2.135 dB at tau 0.5 / 5 / 30 ms on a 100 ms ramp, a slope with no knee anywhere on it. 5 ms is far enough above the detector's 1 ms attack to add something and far enough below the syllable rate that the effect stays tied to transients instead of becoming a third level control.
  - **Absent at zero, not flat** — the same rule the emphasis pair and the asymmetry offset follow, so the shipped patch is bit-identical to the build before this existed. Mutations caught: a state moving at audio rate (0.01 ms — it would be a nonlinearity wearing an envelope's clothing), the threshold rising with drive instead of falling, drive measured on absolute level instead of relative to the threshold, and **dropping the knee normalisation**, which passes every other assertion while letting the threshold fall by tens of dB — pinned by asserting the depression stays inside `HYST_MAX_DB` and never goes the other way.
  - **WHAT IT DOES TO THE SOUND: it is a depth control AND a selectivity control, and on real narration the selectivity is the bigger half.** Measured on a 35.5 s narrator clip at the shipped Headroom 6.5, knob 0 → 50 → 100: peak GR **2.97 → 3.42 → 3.93 dB**, residual **−34.0 → −32.2 → −30.5 dBc**, output crest 18.71 → 18.22. Loudness does not move — output RMS travels **0.02 dB** across the whole knob (−21.69 → −21.71) while output peak comes down 0.5 dB, so an A/B needs no re-trim.
  - **DEPTH-MATCHED IT IS NOT A HEADROOM OFFSET, which is the finding that justifies the control.** Binary-searching the hysteresis-0 Headroom that reproduces hysteresis-100's peak GR: at Headroom 6.5 the knob is worth **1.8 dB of effective headroom** (4.72 matches it), and at the same 3.93 dB of peak reduction it adds **2.0 dB less distortion on half as many samples — 1.61% against 3.34%**, keeping 0.5 dB more output crest. At Headroom 4 the gap widens: 5.12 dB of peak GR either way, **−22.94 dBc on 4.99% of samples against −21.24 dBc on 11.88%**, a 2.4× difference in how much of the file gets touched. Lowering Headroom works on everything; the memory concentrates the same depth on the transients that charged it.
  - **THE ONSET BIAS RE-MEASURED AT MATCHED OUTPUT PEAK, and it partly rehabilitates the knob.** Every onset figure recorded below was taken at matched *Headroom*, i.e. confounded with depth. Matched on output peak instead (both −2.765 dBFS, Headroom 6.98 against 7.50): total residual **−35.73 → −34.67 dBc** (the ~1 dB cost), but split by whether the envelope is rising, **onsets −28.54 → −27.24** and **sustained speech −50.50 → −53.08**. So the knob does not simply add 1 dB of distortion: it moves **2.6 dB of it OFF sustained speech and 1.3 dB ONTO onsets**, widening the onset advantage from 21.97 to 25.84 dB. Whether that is a good trade is a perceptual question the energy total cannot answer — sustained speech is arguably where distortion is most audible — so the "remove it" case is weaker than the headline figure suggests.
  - **The bias toward onsets is measurable directly.** Splitting on whether the envelope is above its own value 40 ms earlier, residual on onsets runs **21 dB hotter than on sustained speech** (−26.9 vs −47.9 dBc at knob 0), and the knob widens that gap a further 1.3 dB. That is the difference from a compressor: this leaves the body of a phrase where it was.
  - **⚠ ELEVENTH TIME SYNTHETIC MATERIAL FAILED TO ANSWER THE QUESTION, and this time by understating rather than exaggerating.** On `variedSpeech` at the shipped Headroom the stage produced **0.10 dB** of peak GR against the real file's 2.97 — it barely engaged at all, so every ratio was measured in a regime the stage never operates in. The synthetic depth-matched comparison showed the selectivity as 11.5% vs 13.2% of samples, a difference small enough to dismiss; the real file shows 1.61% vs 3.34%. **The direction was right and the magnitude was off by more than an order of magnitude.**
  - **⚠ AND ONE OF THE STATISTICS WAS BROKEN ON REAL AUDIO.** "Samples touched", measured as output-minus-input past a relative floor, read **80%** on the real file — because the oversampler's reconstruction error touches every sample whether or not the curve fires, and on real material it clears any relative floor. Isolating the curve by differencing against the same render with the threshold at 0 dBFS (so the oversampler error cancels) takes the same figure to **1.5–5%**. A metric that saturates reports nothing; it happened to work on synthetics only because their pauses are near-silent.
- **EQ** — parametric, 12 bands, live analyzer. One strip per band (gain knob, filter shape, frequency and width knobs) with all bands on screen at once; shape options are positional, so cuts and shelves are offered only on the lowest and highest bands. Opens on a neutral four-band starting layout.
- **Spectrum Analyzer** — the conventional RTA display, and deliberately not a new one. Every other plot in the app answers a question specific to its plugin and earned its shape; this one exists so that someone who has used an analyzer before can read a file without being taught anything. It taps the **effect chain's output**, not a plugin's — each effect window already shows its own output with everything downstream missing, and the question here is "what does this file sound like right now", so it sits where the ears do. Asking for the chain is also what makes it work on a file with no effects engaged: playback only routes through the chain if one exists.
  - **The FFT is resampled onto a log grid before it is drawn, taking the LOUDEST bin per cell.** At 4096 points and 44.1 kHz the bottom octave is two bins spread across a tenth of the display and the top octave is 926 bins crammed into the same tenth — drawing the raw array overdraws the right-hand tenth and interpolates a straight line across the left. Max rather than mean because what is being looked for up there is usually narrow (a whistle, a ring, a switching supply), and averaging it with thirty quiet neighbours is exactly how it disappears; broadband noise reads slightly hot, which is the safe direction. Cells finer than a bin interpolate, or the bottom octave draws as a staircase. Bin 0 is never drawn — it is DC, and letting it into the first cell paints a permanent wall at 20 Hz.
  - **The vertical window is a control, not a fit.** An analyzer that rescales itself turns "the hiss got quieter" into "everything moved", which is the one comparison it exists to support — same reasoning as the resonance display's fixed window. Tilt (0/3/4.5/6 dB per octave, anchored at 1 kHz so it is not a second level control) is the setting that makes a falling spectrum readable; 3 dB/oct puts pink noise flat, and the test asserts exactly that.
  - **Peak hold ages per cell**, for the reason ResoTame's does: one shared timer is reset by any of 384 cells rising, one always is, and the hold never reaches its decay phase. `test/dsp/spectrumDisplay.test.js` pins both that and the tone-survives-resample property.
  - **Off-scale readouts say so** — `getFloatFrequencyData` does not clamp to `minDecibels`, so silence reports numbers like −196 dB, which reads as a broken meter rather than as silence. Below the window it prints `< -100 dB`.
  - **The tap is released on unmount, not on the close button.** Escape reaches the window manager directly and pops a window without anyone emitting `close`, so a teardown wired to the button leaks an AnalyserNode that keeps being pulled for every quantum of every playback for the rest of the session.

The cepstral reference works in a band roughly **150–900 Hz and nowhere else** — blind below the fundamental where rumble and room modes live, and blind above ~1 kHz where sibilance and ring live. That is most of what a resonance suppressor is asked to remove.
  - **THE FIRST EXPLANATION OFFERED FOR THE HIGH END WAS WRONG, and the measurement that killed it is the useful part.** The cepstral envelope's resolution is uniform in Hz, so the obvious theory was that it tracks — and therefore hides — resonances that are wide in Hz. Swept at 6 kHz by bandwidth, cepstral removes **0.03 / 0.00 / 0.01 / 0.01 dB at Q 40 / 20 / 8 / 3** against peak's 6.08 / 6.33 / 6.05 / 4.96. Bandwidth is irrelevant; it does not see anything up there at any width. The remaining explanation is **unproven**: cepstral compares a RAW bin against a smooth envelope, and at high frequencies the raw spectrum's own bin-to-bin scatter is comparable to the threshold, where the peak path compares a max-filtered value against a wide octave-scale average.

Near an edge the label slides inward and grows a leader; **the dot stays at the true frequency**, because the dot is the measurement and the label is the annotation.
  - **⚠ THE PILLS ARE BEHIND A CLICK NOW — DOTS ALWAYS, ONE LABEL ON DEMAND.** Every mark used to carry its label all the time, which meant up to four fixed-size objects re-placed four times a second, each carrying a depth that changed every frame, sitting on the one curve the panel exists to show. Reported as distracting, and the mechanism is that a label does not scale with what it names: four of them cover a real fraction of the plate whatever the audio is doing, so the display was busiest exactly when the effect was working hardest. **The dots stay** — they are what says a peak was identified as a resonance rather than as ripple, they are the target, and a reveal whose trigger is invisible is not discoverable at all (hence the `pointer` cursor over one, the same argument the selection edges' `ew-resize` makes). Clicking a dot names it, clicking it again puts the label away, clicking anywhere else clears it — and a dot **takes the click from the zone underneath**, because a click that lands on a 12 px target should do one thing. **Selection is held as a FREQUENCY, not an index**, so it survives the mark set being republished 4x a second (nearest within 1/6 octave); a named resonance that goes quiet **keeps its selection and loses only its pill**, because an intermittent ring is the hardest kind to catch and the one whose name most needs to stay put. **Up and down walk the resonances, including an off position**, so the frequencies are reachable without a pointer — the accessible name can describe a zone's settings, but a resonance's frequency exists nowhere else on the panel. That name now lists every tracked resonance for the same reason, and it **stopped saying `Processing NaN Hz to NaN Hz`**: the sentence read `freqFloorHz`/`freqCeilHz`, props that went with the low/high Range fader, so `formatHz(undefined)` rounded to NaN and every screen reader landing on the canvas heard it.
  - **THE PLOT NO LONGER DIMS WHEN THE TRANSPORT STOPS.** It faded to 0.3 after 300 ms with no new frame, on the argument that a frozen frame is still true about the moment playback stopped and that dimming reads as *not moving* where blanking reads as broken. Right about the fading, wrong about what the plot is for: with the marks now revealed by clicking one, **a stopped transport is exactly when the display is read** — playback stops, and then you go and find out what that ring at 3 kHz was. A picture whose dots are dimmed to a third while you aim at them is at its faintest precisely when it is being studied. What says the transport is stopped is the transport.

  - **The range-bracket control from the source design was deliberately not taken.** Zones already do that job, they do it per band with their own settings, and two mechanisms that can both exclude a span is one too many — the same argument that removed the low/high Range fader.
  - **ONE LANE, WITH REDUCTION AS THE HERO — it was two, and the split was backwards.** The reduction lane took 36% of the plot and the spectrum 64%, on the argument that reduction is one curve against a scale where the spectrum is three against each other. True, and beside the point: the two were drawn on scales four times apart in sensitivity, and **the big one could not resolve the effect at all**. The spectrum spans 90 dB (−102…−12), reduction spans 24 on a voltage law, so at 280 px per dB of actual cut the reduction lane gave **19.9 / 50.8 / 62.6 px at 3 / 9 / 12 dB** against the spectrum's **5.5 / 16.6 / 22.1**. The SMALLER lane was **3–4× more legible per dB**, and the shaded sliver between input and output — the one element that claimed to show removed resonance — rendered at about **5 px at the stock mean cut**, the thickness of the strokes around it. It said something had happened and could not be measured. Two thirds of the display was spent on the file and the decision boundary, which is the *explanation* of a cut rather than its *result*.
  - **The two do not fight for ink as much as it sounds.** The spectrum window tops out at −12 dBFS while per-bin speech peaks sit near −35, so the top quarter of the plot is normally empty and that is exactly where reduction hangs. A cut deep enough to reach into the trace is a cut deep enough to be worth seeing there. Verified in a real browser at light and heavy settings before shipping — the fill is lighter than it was in its own lane precisely because it now covers ground with something under it, and the 1.5 px stroke carries the reading.
  - **The output curve and the sliver went with the split.** Output is the input minus the same reduction, and a third curve tracing the input everywhere the effect is idle is ink spent on agreement. What remains is the pair the reduction curve cannot say by itself: what the file has, and where the line was drawn. ⚠ **The kernel still computes and posts `output`** — summarised per display cell from its own bin rather than derived, which is a real distinction worth keeping until the new display has been listened to. Nothing draws it; the component no longer smooths it.
  - **THE REDUCTION TRACE IS DRAWN ONLY WHERE THERE IS A CUT, and that is not cosmetic either.** In its own lane a continuous stroke along the top read as that lane's zero datum; across the full plot the same line reads as a frame edge, or worse as activity — the identical argument the peak hold already made for itself. Broken at the same **0.3 dB** the per-zone readouts and the hotspot line use, so trace and numbers appear on the same frame. **Each segment opens on the bin before it crosses and closes on the one after**: starting at the first bin over the threshold was tried and on a resonance a few bins wide the curve is already several dB down by then, so the trace began mid-descent and drew a stub instead of a trough.
  - **DELTA is expressed on the reduction fill now the sliver is gone**, which is its natural home rather than a substitute for one: in DELTA the removed signal is what is being heard, so the curve bounding it is the thing to light up.
  - **The display is per-zone now, because the detector was multiband and the readout was not.** Each zone prints its own deepest cut at the top of its own column, and the readout line scopes to the selected zone (`Z2 180 Hz–1.10 kHz · -4.1 dB`) instead of a single global `PEAK <hz> · -<db>` spanning the whole spectrum — the same objection that got the gain-reduction meter replaced by this plot in the first place, quietly reintroduced in the text line above it. In practice the global line almost never appeared anyway: a zone is essentially always selected and `zoneText` wins the slot. **Deepest cut rather than the zone's mean**, which is dominated by the bins the effect is correctly leaving alone and reads near zero whatever is happening. **A silent zone reads `OFF`, not `-0.0`** — zero is a measurement, and a bypassed band reporting it says the effect looked and found nothing when the truth is that it never looked; a zone silenced by another zone's delta is read the same way, since it is still `enabled`. Columns narrower than 30 px carry no number rather than a clipped one that can be misread as the neighbour's. The arithmetic is `zonePeakReductions` in `resonanceZoneEdit.js` rather than the component, per the same rule as the rest of the zone geometry: a cut attributed to the wrong column looks exactly like one attributed to the right column.
  - **The zone stock carries peak's calibration and it is NOT yet listened to** — `selectivity: 20, depth: 1` are the peak reference's previous real-audio calibration (protection off, old F0 tracker); a fresh solve on the same clip puts the 3 dB point nearer **16.3**. `sharpness` and `maxCut` were never re-derived against the peak envelope at all, and sharpness means something different there — the geometric window of the peak reference rather than a cepstral lifter cutoff.
  - **`protect` now defaults OFF, and that is behavioural rather than a number.** The mask exists because the cepstral reference sits at the inter-harmonic floor; the peak envelope is drawn THROUGH the harmonic peaks, so nothing protrudes at a harmonic and there is nothing to protect against. Switched on under peak it **inverts** — partials held, the floor between them attenuated — which is pinned in `resonancePitch.test.js` and measured not to improve the harmonic-to-noise ratio on real narration.
  - **The panel relabels the mask per reference, because it is not the same control under the two.** `PRESERVE HARMONICS` / `PROTECTION OFF` with an amber warning under cepstral, where turning it off really does thin the material; `BETWEEN PARTIALS` / `ACROSS SPECTRUM` with no warning under peak, where its off state is the normal one.
  - **The kernel tests pin `refMode: 'cepstral'` explicitly.** They were written and their thresholds derived against it, and they measure what the two references share — threshold, knee, depth, spread, mask, mix — which all sit downstream of the envelope. Pinning the mode means the shipping default can move without silently re-tuning what they measure; half of `resonancePitch.test.js` is the evidence for this swap and would say nothing if it followed the default.
- **ResoTame** — dynamic resonance suppression, with a **per-frequency display in place of a gain-reduction meter**. A compressor pulls everything down by one amount, so one number describes it; this cuts a handful of narrow bands and leaves the rest alone, where "6 dB" cannot distinguish a surgical notch from 6 dB taken off half the spectrum. ONE lane over a log-frequency axis (`src/components/meters/ResonanceSpectrum.vue`) showing **removal only**: the reduction curve hangs from a 0 dB rail on the same voltage-law scale the other panels' GR meters use, with a decaying per-bin peak hold that makes an intermittent ring findable, and the deepest resonances named by frequency. Grid, carve history and input spectrogram are optional overlays rather than part of the default. **The curves are the kernel's own numbers, not a second analyser on the output** — an FFT of the output could show the result of a cut but never the reference it was decided against, and that reference is the whole explanation of why a peak was or was not treated. **The drawn curves are averaged with a 103 ms time constant** — the Spectrum Analyzer's *averaging* knob at 85%, stated as a time constant rather than a per-frame pole because this plot is fed at ~23 ms and drawn on rAF, two rates that need not agree (it was 75 ms, i.e. 80%). The kernel resamples its frame onto a 192-point log grid and posts **five curves** with the meter message (`readDisplay`, ~46 Hz): magnitude, reference, output, live reduction and held reduction. Magnitude is normalised to dBFS. **The output curve is sent, not derived as `magnitude − reduction`** — those two summarise a display cell from different FFT bins (loudest vs most suppressed, different bins in 65% of the cells carrying any cut on real speech), so subtracting them draws a notch up to 2 dB deeper than the one that happened. ⚠ **Nothing draws that curve since the lanes merged** — it is still computed and posted, and kept for now because the distinction above is real and the merge has not been listened to yet; strip it from `readDisplay` once it has. Reduction is sent twice for a related reason: the live curve agrees with the spectrum beside it, and the held curve — the maximum since the last read, so a peak landing on an unread frame is not lost — feeds the peak-hold outline and nothing else. **The peak hold ages per bin.** One shared timer was tried and is broken by construction: it resets whenever any of 192 bins rises, something always is, so the trace never reaches its decay phase — an intermittent 3 kHz ring still read full height three seconds after it stopped, against 0.49 → 0.37 → 0.16 with per-bin ages. Side effect worth knowing: with `PROTECTION OFF` the display shows the suppressor eating the harmonic comb, so the warning that it thins the material is now visible rather than only asserted. **A `DELTA` monitor sits beside ON/BYPASS in the header** — audition only what is being removed. It applies the *complement* of the gain inside the same STFT (`ResonanceKernel.setMonitor`) rather than subtracting two signals downstream: the transform is linear and reconstructs exactly, so `ISTFT(X·(1−G))` is `ISTFT(X) − ISTFT(X·G)` sample for sample, with no delay to align and no second path to drift (pinned in `resonance.test.js` — output + delta reconstructs the input to 7e-9). **⚠ THE COMPLEMENT IS TAKEN AGAINST THE TRIM, NOT AGAINST UNITY, and `1 − g` was a real bug.** `gain` carries the output trim (`gain = trim·((1−mix) + mix·g)`), so on a patch removing NOTHING — every zone bypassed, depth at zero — the complement of unity is `1 − trim`, which is not zero unless the trim is. Reported from use as *DELTA keeps playing the file with everything switched off*, and it did: measured on a 180 Hz tone at 0.2, delta peak **0.199 at +6 dB of trim** (the whole file, at full level, polarity flipped), 0.058 at −3 dB, 0.000 at 0. It is `trimLin − g` now — the same arithmetic with the trim factored out of the complement and left on the result, so the delta is the removed signal monitored through the same output trim the processed signal is, and it is **silent whenever nothing is removed, at any trim**. Mix needs no such treatment: it scales how much is removed, so a delta that goes quiet as Mix falls is correct. The cost is the exact form of the identity — **output + delta is now the TRIMMED input** rather than the input — and at the default 0 dB it is bit-identical to what it replaced. Both halves pinned. **It is not a parameter and must never become one**: `applyResonanceRegion` spreads its param object straight into the kernel, so a monitoring mode living in `params` would be one careless key from rendering a difference signal into the timeline. It travels on its own port message, which the offline path never sends. **The display cost the panel 175 px it did not have** — everything below the fold was reachable only by scrolling, which pushed Depth off the top — so the faceplate was compacted to fit a 800 px viewport with no scroll: the plot split its height between the lanes by ratio rather than at a fixed 56 px (there is one lane now — see above), its readouts and legend share one line above the plot instead of two either side of it, and Low Limit / High Limit merged into one two-handle log-frequency fader (`src/components/knobs/DeviceRangeSlider.vue`) — the lit span between the handles is the processed band. **Each handle stops at the other one and at nothing else.** It first kept the old per-parameter limits (low ≤ 1 kHz, high ≥ 2 kHz) on the argument that merging two faders is presentational and must not widen what the effect can be set to — wrong about how the merged control reads: on two faders a limit is where that fader ends, on one shared track a handle stopping dead with track visibly in front of it reads as a jam. A closed band is therefore reachable and means the effect processes nothing, which is legible rather than silent because the display washes out everything outside the band. Handles that can meet can also hide each other, so z-order goes to whichever still has somewhere to go. **A range input is not a controlled component** — the browser moves its thumb with the pointer and fires `input` afterwards, and Vue patches `:value` only when the bound value *changes*, so the moment a handle reaches the other one and the clamp starts returning the same frequency there is nothing to patch and the thumb sails past the stop and stays there. `syncThumbs` writes the accepted position back after every event, which is what makes the stop real. **Separately, `FloatingWindow` now says when a panel runs past the fold** (`MORE ↓` over a fade, measured from the DOM): a window taller than the viewport always scrolled, but its hairline scrollbar plus a faceplate's hard bottom edge made a panel with controls below the fold look like a panel without them — reported twice as a control that had vanished. Shortening a panel fixes one viewport; saying so fixes every viewport. **THE ATTACK AND RELEASE MAXIMA WERE INHERITED, NEVER MEASURED, AND ARE NOW 400 / 2000 ms — AND THE DEFAULTS ARE 300 / 1500, UP FROM 15 / 80.** 15/80 came from the server stage, where the suppressor runs inside a chain rather than as something set by ear; the sweep below is the argument for the slow end, and the defaults now sit where it points. Long ballistics were found by hand to suppress the pitch artefacts that appear with `PROTECTION OFF`, and the sweep says the credit is misassigned: at fixed selectivity, longer attack gets **worse** per dB removed (0.351 → 0.417 from 12 to 800 ms) and at 800 ms removes 0.87 dB, barely above the mask-on config's 0.20 — it is a throttle, not a cleaner. Longer release genuinely improves per dB (0.416 → 0.299 out to 4 s). **Matched at 3.0 dB of cut the whole effect is modest and saturates** — jitter 0.96/1.29 at 12/80, 0.80/1.02 by 200/500, then flat to 200/4000 — so the large raw-sweep numbers were the throttle, not the ballistics. What keeps improving is **p90 depth, 8.5 → 5.2 dB**: the same average cut spread evenly instead of concentrated in momentary deep notches, which is the plausible reason the artefacts are audible at all and the reason to raise the tops. 400/2000 captures nearly all of it; 800/4000 is marginally better (0.73/0.90) but needs selectivity at 13.5 to hold the cut and an attack near a second no longer tracks a phrase. **Pause bleed falls rather than rises at matched cut** (−2.47 → −1.19 dB), because the higher selectivity a slow setting needs more than pays for the longer tail. **RESOTAME IS A MULTIBAND DETECTOR NOW: THERE IS NO GLOBAL DEPTH, SHARPNESS, SELECTIVITY, MAX CUT OR HARMONIC PROTECTION.** Each zone carries all five as absolute values, and the panel shows one set of knobs for whichever zone is selected — the arrangement a multiband compressor uses, for the reason it uses it. Two designs were tried and discarded on the way, and both failures are instructive.

  - **Gaussian nodes, discarded.** A node was a bump at a centre frequency with a width in octaves, drawn as a dip in the threshold line and dragged there. **(1) The handle rode the threshold curve, which is `reference + offset` and therefore moves with the audio at ~46 frames a second** — reported from use as a control bouncing three or four times a second and impossible to aim. A control cannot live on a moving curve. **(2) The parametric-EQ gesture promised something this tool cannot do.** Click anywhere, get a bell — that reads as "pinpoint a frequency and notch it", and a node never notched anything: it moved a detection threshold, so on a clean part of the spectrum it did nothing at any setting. The gesture was borrowed from a control whose value is gain; this one's value is not gain. **A fixed notch at a measured frequency is the EQ plugin's job**, and pointing at it there is the honest answer.
  - **Per-zone strips, discarded.** Three settings across up to six zones is eighteen values competing for one row, which forces each into something too small to be a control — the version that shipped printed them as numbers and had to be explained, then as filled tracks, and was still cramped. One zone's controls at a time, selected on the plot, is what the reference designs do.
  - **The dividers are full height and that is the whole zone UI on the plot.** A zone is a COLUMN of the display; its boundary is a line you drag; **its dot along the bottom selects it**. The 38 px lane that used to hold an editable value is gone — it cost a third of the spectrum lane to say something the knobs now say better. **Nothing in the display is a value editor any more**, so no click in the plot can change the sound by accident; clicks select, drags move boundaries, double-click splits or merges.
  - **⚠ SELECTION IS A DOT PER ZONE NOW, NOT A TINTED COLUMN.** The selected column used to carry a 7% wash of the accent, and two things were wrong with that. It is a WHOLE-COLUMN statement about an area already carrying three others — the veil over a silent zone, the reduction fill, and the waterfall with the overlay on — so the faintest of them was the one asked to say which zone the knobs were editing. And **a wash is not a target**: it says which zone is selected and nothing about how to select another, which left clicking-anywhere-in-a-column an undiscoverable gesture. A dot is both at once, and it is the same vocabulary the resonance marks use one layer up — filled for the selected one, ringed for the rest, `pointer` on hover. It sits **at the bottom** because reduction hangs from the top and the per-zone numbers are printed there, and above the dividers' lower grips rather than beside them, since a zone dot and a boundary grip are different gestures. **Clicking the plate anywhere in a column still selects it** — the dot is the signpost, not a narrowing of the gesture — and a bypassed zone's dot carries a slash, because the dot is the one part of a veiled column drawn at full strength. Geometry in `resonanceZoneEdit.js`, pinned in `resonanceZones.test.js`: a dot in the wrong column looks exactly like a dot in the right one.
  - **1–6 zones, three by default** (splits at 180 Hz and 1.1 kHz — the two the panel's own reasoning rests on, below the first being where rumble and the fundamental live and above the second where sibilance and ring do; the old 5 kHz split folded the upper mids and air together), **added and removed with a `−  n ZONES  +` pair that acts on the SELECTED zone.** It was a row of the numbers 1 to 6 with the current count lit, borrowed from the reference design, and it read as a selector for which zone was active — six numbers beside a row saying ZONE 3 cannot help but look like a way to choose zone 3. A pair of buttons around a count cannot be misread that way, and acting on the selection makes both predictable: plus splits the zone you are looking at at its geometric centre, minus folds it into its neighbour — the same two edits the plot's double-click makes. A split inherits the zone's settings, because it means "this span needs to be two spans", not "throw away what I set here".
  - **PER-ZONE DELTA REPLACED PER-ZONE SOLO, and it is the same transform with the opposite monitor.** Solo isolated a zone and played what SURVIVED it; this isolates a zone and plays what it TOOK OUT — every other zone off, plus the kernel's delta monitor, so what comes out is that band's cut and silence everywhere else. Solo answered *what does the file sound like with only this band worked*, which the global bypass already answers; the question a suppressor is actually asked is *what is this band removing*, and that needs the delta scoped to a zone rather than to the whole effect. **IT IS A MONITORING STATE AND MUST NOT BECOME A PARAMETER, and it is the more dangerous of the two the panel has.** The header's DELTA is expressible only inside the kernel; the isolation this rides on is expressible as ordinary parameters — every other zone at depth zero — so nothing about it would *look* wrong if it leaked into what Apply renders. It would simply write a one-zone pass into the timeline. `liveZones()` applies it on the way to the live kernel only; `currentParams()`, which is what `applyResonanceRegion` receives, never consults it, and `test/ui/resonanceZoneDelta.test.js` pins that by reading the source. Cleared on teardown for the reason the header's delta is: the effect entry outlives the panel. **One kernel monitor, two controls**: `monitoringDelta()` is the OR of them, so a zone delta forces it on regardless of the header switch and hands that switch back untouched when it clears — otherwise switching a zone's delta off would silently turn the global one off with it. **Asking a bypassed zone what it removes means silence, deliberately** — a fair question with an honest answer. **Bypass and delta are lettered differently on purpose** (`ON`/`BYP` in the accent, `DELTA` in amber): bypass is stored and rendered, this is not, and two identical lamps would say they were the same kind of control.
  - **The plot washes out whatever is not sounding**, whether that is a bypassed zone or every zone but the one whose delta is being heard — a display that did not follow it would disagree with the speakers. That index reaches the plot as its own prop rather than baked into `zones`, so the knobs keep reading the stored settings.
  - **The low/high Range fader is gone.** A band you want left alone is a zone switched off, and two controls that can both exclude a band is one too many. What remains is `ANALYSIS_FLOOR_HZ = 20`, an analysis bound rather than a taste: below it a 2048-point frame has under two bins to work with. The harmonic-protection walk now runs to Nyquist, so the mask depends on F0 alone and its cache never needs clearing — the golden bin counts in `resonance.test.js` were re-recorded for it.
  - **SHARPNESS IS THE EXPENSIVE ONE, and it is priced by DISTINCT VALUES, not by zones.** Depth and selectivity are per-bin numbers; sharpness sets the scale of the reference envelope, which is a property of a whole transform. So each distinct sharpness among the zones needs its own envelope — the forward cepstrum is shared, so the cost is one extra inverse transform per distinct value per frame, at most five. Three zones sharing a sharpness cost one. `buildResonanceZoneCurves` returns those groups with a per-bin weight each; the kernel blends the envelopes by the same weights that crossfade every other zone setting.
  - **The uniform case ASSIGNS rather than blends, and that is a guarantee rather than an optimisation.** Summing N identical envelopes by weights that sum to 1 differs from the envelope in the last bits, so a panel still on the stock settings would drift from the pre-zones build by an amount that is inaudible and impossible to prove absent. With one group the kernel assigns. **Pinned: the four default zones are bit-identical, sample for sample, to a single zone carrying the same numbers.**
  - **HARMONIC PROTECTION IS PER ZONE, and the measurement is the whole argument.** The mask zeroes reduction near every harmonic of the measured F0, and its coverage does NOT fall off with frequency: measured at F0 90 / 140 it blocks **67–77% of every octave from 60 Hz to 20 kHz**, and at F0 220 it blocks **88% above 10 kHz**. Down where partials are wide and dominant that is real protection — thinning the comb is exactly the damage it exists to prevent. Up where sibilance and hiss live it is a blanket veto over the band, and the "harmonics" being protected are a comb too dense to separate by ear. So *protect the fundamental region, work freely above 5 kHz* is the setting this effect most wants and could not express. It is applied as a per-bin WEIGHT (`reduction *= 1 - protect[k]`) rather than a flag, so a boundary between a protecting zone and an unprotected one crossfades like every other zone setting; the mask itself depends only on F0, so one zone asking for it pays for the whole thing. **THE PITCH RANGE IS FIXED AT 70–400 Hz AND THE VOICE/WIDE SWITCH IS GONE.** It was global on the argument that nothing else about the effect assumes speech and this should not either — a true premise, wrong conclusion. The EFFECT is general-purpose; the MASK is not. It is a comb built from one tracked F0, so it is a voice feature whatever the effect is pointed at, and **WIDE was measurably worse on the only material the mask is for**: on 46 s of real narration the two settings disagree on **18.6% of frames**, with WIDE's p90 at **849 Hz** against a real median of 191 — a comb at the wrong spacing protects the wrong bins and leaves the actual harmonics exposed. WIDE earns its place only above 400 Hz, where VOICE cannot track at all (500/800/1000 Hz sources read as 250/400/333), and a pitched source up there is not what the mask was built for. Its advertised 40 Hz floor was fiction besides — nothing below ~70 Hz resolves in a 2048-sample frame, and 45/55/65 Hz sources report no pitch under either setting. **A zone whose content is not a voice switches protection off rather than retuning the range**, which is the control that already exists. The range is printed in the mask panel rather than chosen, so the fact stays visible. **It is still global and it no longer sits with the global controls**, because it is unreadable apart from the switch that turns the mask on — the two are one decision (what counts as a harmonic here, and what pitch to look for) and they were on opposite sides of the faceplate. Both now live behind a **`HARM ›` door in the zone block**, which SWAPS PLACES with the zone's identity rather than expanding beside it: the row's height is set by the knobs, so opening it moves nothing. **The closed door is tinted amber whenever any zone is unmasked**, which is the one thing a hidden control must not cost — the state stays visible without opening it. It closes on Escape and on selecting another zone, since the protection toggle inside is per zone and a door left open on Z2's harmonics beside Z4's identity would be showing two zones at once.
  - **Max Cut is per zone too**, because the honest ceiling differs by band: a low-mid resonance can lose 12 dB before it is obviously gone, where the same number spent on sibilance is a lisp. It is a field rather than a dial, beside the zone's three knobs.
  - **The panel-level warning survived the control moving.** With protection distributed to the zones there is no global button left to carry a caption, but this is still the one setting that can quietly wreck the material and a per-zone lamp is a small thing to notice — so the sentence appears in the global row whenever ANY zone has it off, and names the zones. **Trim moved next to the output meter**: the meter says what the level is and Trim is what moves it, and they were two rows apart.
  - **DEPTH AND THE CEILING ARE APPLIED ONCE, AFTER THE SPREAD KERNEL.** Applying depth in the detection loop let a neighbouring zone's reduction smear through a boundary — the spread reaches 96 bins either side, and a zone switched off still lost **0.68 dB on a tone 1.6 octaves clear of the edge**, which is not what OFF can mean. Moving it costs nothing, because the spread is linear and scaling before or after is the same arithmetic wherever depth is uniform. The one real change is that `maxReductionDb` now clips the finished reduction rather than an intermediate, which is where a ceiling belongs. **A first attempt applied depth in BOTH places and squared it** (0.67 → 0.449 on the default patch); the existing suppression tests caught it.
  - **Boundaries crossfade over 1/6 octave, and that is not cosmetic.** A hard step means the bin below a split and the bin above it are judged by different rules, so a resonance sitting across the line is half treated and slides between the two regimes as the pitch moves — the same per-bin gain movement the whole effect exists to avoid. Two semitones is wide enough that no single partial spans it and narrow enough that an edge still lands where it was put. The weights sum to 1 at every frequency, which is what lets a threshold, a depth and a whole envelope be blended by the same numbers.
  - **`uniformZones()` is the shape for callers with no opinion about frequency** — a preset block, a test, code that predates zones. Not a compatibility mode: the kernel has one path and this is what "the same everywhere" looks like in it.
  - **THE ZONE BOUNDARIES ARE FITTED TO THE VOICE NOW (`FIT TO VOICE`), AND THE SHIPPED SET TURNED OUT TO BE THE MALE REGION TABLE.** The shipped boundaries were placed "where the voice changes character", and checked against `MALE_REGIONS` that is literally what they are: 180 is `body_warmth`'s geometric centre (183.3) and 1100 is within an eighth of an octave of `lower_presence`'s bottom (1200) — and the 5000 that shipped before the three-way split was **exactly `upper_presence`'s top edge**. VoiceRx already measures what they stand in for — its tables MOVE with the voice, and `classifyVoice` interpolates between them continuously — so on a female narrator every boundary sits **0.26–0.47 octaves low** and her fundamental at ~220 Hz falls in z2 rather than z1: the zone whose whole purpose is the fundamental region does not contain her fundamental.
    - **THE UPPER BOUNDARIES ARE A RATIO, NOT A FREQUENCY.** Each is scaled by its own anchor's ratio against the male table, so **a male voice reproduces the shipped upper boundaries exactly** and nothing already listened to moves. Measured: male F0 110 → `60 / 200 / 1100`, female F0 210 → `100 / 280 / 1375`, F0 170 → `94 / 210 / 1137`. **The fundamental boundary is not one of them — see the Z2 bullet below.** No new constants — every number comes out of `regions.js`, and the calibrated set is read off `DEFAULT_RESONANCE_ZONES` rather than repeated, so the scaling cannot end up anchored to numbers the app no longer ships.
    - **THE SUB-FUNDAMENTAL REGION IS PARTITIONED OFF — one more zone than the shipped set, four against today's three.** Below the corner there is no voice but there is very often HVAC, traffic, handling and plosive thump, and while it shares a zone with the fundamental it is not separately controllable. It is not only shared settings: **the spread kernel reaches ±96 bins and runs BEFORE per-zone depth**, so a deep cut taken on a 45 Hz rumble smears up into the fundamental unless a boundary confines it. EQ is usually the better answer down there and this does not pretend otherwise — but not every file arrives high-passed.
    - **⚠ Z2'S TOP WAS SIZED BY SOMETHING THAT DOES NOT KNOW WHERE THE FUNDAMENTAL IS, and it is `min(2.5 × F0, mud's bottom edge)` now.** It was `body_warmth`'s geometric centre — a region-table anchor with no relationship to a harmonic series. Measured across F0 90–240 it contained the fundamental every time and **the second harmonic exactly never** (2F0 landed above the boundary at every F0 above 90), and the headroom above F0 collapsed as the voice rose: **0.71 octaves at F0 110, 0.42 at 150, 0.17 at 170, 0.04 at 240**. `HARMONIC_REACH = 2.5` rather than 2.0 so 2F0 sits inside with margin instead of on the 1/6-octave crossfade, where it would be split between two settings.
    - **⚠ THE CAP BINDS ON ALMOST EVERY REAL VOICE, so 2F0 IS NOT GUARANTEED.** `2.5 × F0` only comes in under mud's bottom edge below about **F0 80** (male table) or **F0 112** (female), so for a typical narrator Z2 ends exactly where mud begins — **200 Hz male, 280 Hz female**. At F0 110 the second harmonic is 220 and the boundary is 200, so it falls into Z3; reaching it would mean Z2 running to 275 and taking the bottom of mud with it. The reach is best-effort and the containment below is the guarantee — which is the trade that keeps Z3 meaning "mud, boxy, nasal".
    - **`MIN_F0_MARGIN = 1.2` OUTRANKS THE CAP, AND IT FIXES A ZONE THAT EXCLUDED ITS OWN FUNDAMENTAL.** `classifyVoice` saturates — every voice above F0 200 gets the female table — so a cap read off that table is CONSTANT while F0 keeps rising, and at F0 340 the old anchor put Z2's top at **251 Hz, below the speaker's fundamental**. Headroom above F0 is now **0.26–1.32 octaves** across the tracker's whole 70–400 Hz range, against 0.04–1.00 before. ⚠ Where the floor binds Z2 **does** cross into mud: intended precedence, since a zone that excludes the fundamental is broken and one that overlaps mud is merely wide. Swept every 5 Hz in the tests.
    - **⚠ SO THE PLACEMENT IS NOT ONE MECHANISM, IT IS TWO.** The corner and the fundamental top are **derived from the measured pitch**; the presence (and, if re-split, sibilance) boundaries are **scaled stock values**. The stock 180 is no longer used for anything. Recorded because "everything is a ratio against the male table" was true of the first version and is not true now.
    - **THE CORNER IS `rumbleCornerHz`, UNCHANGED AND NOT RE-DERIVED** — 0.75 × p25 F0 or 0.55 × median, whichever is lower, clamped to [40, 100] Hz. "Where this speaker's voice stops" has one definition in this codebase and two would eventually disagree. It is the one boundary that is **not** scaled, because it is a statement about the speaker rather than about a region table; pinned by a test that fails when a mutation scales it with the rest.
    - **ONE TRACKER, ONE GATE, ONE POPULATION.** `voiceProfile.js` runs VoiceRx's own `collectVoicedFrames` rather than a private F0 pass, so the pitch the zones are placed from is the same number VoiceRx classifies the voice with **by construction** rather than by two implementations agreeing. Two estimates differing by an octave-halving error would put regions and zones in different places on one spectrum with nothing on either panel saying so.
    - **THE PLACEMENT IS GEOMETRY-ONLY, and that is the honest claim.** Settings are carried over from whatever zone used to cover each new span — `splitZone`'s rule generalised to a re-partition — so on an untouched panel every zone still carries identical settings and **the curves are unchanged to under 1e-9** (not bit-identical: the extra boundary adds one more crossfade where equal values are blended by weights summing to 1 rather than assigned). It changes no sound. What it buys is the ability to make it change sound.
    - **⚠ THE SHIPPED ZONE SET IS NOT A FIXED LENGTH, and assuming it was cost this a silent failure.** It was three boundaries when the placement was written; the panel folded the upper-mid and air zones together and ships two, and a hard `length !== 3` guard turned that into `placeResonanceZones` returning null — FIT enabled, pressed, and doing nothing, with no error anywhere. The anchors are now read as "one per boundary, low to high", so re-splitting at 5 kHz brings `sibilance` back with no edit. A set LONGER than the anchor list is refused rather than half-scaled: moving the boundaries it recognised and passing the rest through is worse than refusing.
    - **⚠ IT IS NOT WIRED TO SELECTION CHANGES, unlike the soft clipper's ceiling presets.** A ceiling in dBFS is meaningless until placed against material, so it re-measures per region; a zone boundary describes the **speaker**, and re-placing it on every selection drag would move controls the user had set by hand. It is a button, pressed once.
    - **⚠ THE CORPUS CANNOT VALIDATE THIS.** Every real narrator clip on record here is male or near it, so the placement is a near-no-op on all of them — the desired property and also the limitation. Demonstrating it does anything at all needs a female narrator recording, and there isn't one in `data/corpus/`. Verified end to end on synthetic voices at F0 95 / 120 / 210 and in the real panel (F0 120 → Z1 `20–66 Hz`, Z2 `66–200 Hz`).
    - **⚠ A SILENTLY DISCARDED CLICK, FOUND BY RENDERING THE PANEL AND NOT BY READING IT.** FIT was enabled with no selection, `fitZonesToVoice` bailed on the missing region, and the press was accepted and thrown away — **the same failure the ceiling presets shipped once**, in the same panel. It now greys out and prints which of the three reasons applies (bypassed / measuring / no selection). A preset MEASURES THE SELECTED REGION, so the selection is its input, not incidental to it.
  - **Every gesture has a keyboard equivalent** (arrows select, shift-arrows move the boundary, Enter splits, Delete merges), because the only editor for a parameter living inside a canvas is otherwise the one control in this panel some people cannot use at all. **The arithmetic is `src/components/meters/resonanceZoneEdit.js`**, tested in `test/dsp/resonanceZones.test.js` — an axis mapping off by an octave, a boundary drag that lets two dividers cross, or a crossfade that is really a step all still look like a working zone editor.
  - **THE ZONES CANNOT BE PASSED TO THE KERNEL BY REFERENCE, and shipping the nodes that way took the whole display down once.** The param object crosses a structured clone twice — `postMessage` on every knob move and `processorOptions` on the offline render — and the panel holds them in a Vue ref, which hands out a reactive Proxy that `structuredClone` refuses outright. The throw landed on the first param push, so `pushAllParams` never finished: the meter loop never started, `setMonitorDelta` was never restored, and the symptom was **the spectrum plot and DELTA both dead** with nothing on screen about the feature. `copyZones` copies each field, the same thing `manualEq` does with its bands. Pinned against a genuinely reactive array, populated and empty.
  - **A panel showing effective values instead of stored ones lies twice.** `zoneSettings` reports a disabled zone as depth 0 — right for the kernel, wrong for a knob, because switching a zone off would rewrite the number the user had set and switching it back on would look like the panel invented one. Caught twice, in two different components; the controls read stored values and take only `enabled` from `zoneSettings`.
  - **The display got the height all of this paid for: the plot base is 208 px** (140 before zones), the level meters 92, and the global knob row is timing and output only — Attack, Release, Max Cut, Mix, Trim. **Then the controls gave the display 72 px of HEIGHT and the plot base went to 280 px.** Four things paid for it, each measured rather than trimmed by eye. **The input meter is gone** — two meters answer "how much did this change the level", and an effect that cuts a few narrow bands always answers "barely", so the pair spent width to show two columns at the same height. **The output meter moved beside the plot**: a vertical meter is 54 px of scale and labels around whatever bar it is given, so in a row of knobs it was the tallest thing there and set the row height for everything else; alongside the display it gets the plot's full height for free and costs no row at all. **Max Cut and Trim became fields rather than dials** (`DeviceField.vue`) — a knob costs ~70 px of height to express one number and earns it when the number is swept by ear, where a ceiling and an output trim are set once and read often; soothe puts its own max cut and wet trim in the same shape. **And the protection button's caption became conditional**, which is what let it shrink from 186 px and two lines to a lamp: the sentence was there because this is the one control that can quietly wreck the material and a tooltip is invisible to whoever has not already decided to hover — but that argument only ever applied to the dangerous state. "Preserves harmonic frequencies" explains a setting that needs no explaining, so the caption now appears only when protection is OFF, in amber, and the safe state is a lamp. The knee, protection and pitch-range controls share one 26 px line, up from 60.
  - **`DeviceField` is a drag AND a text field, and the gesture decides which** — a press that moves is a drag, a press that does not focuses the box and selects it. That way it is a knob for someone tuning by ear and a number for someone entering a spec, with no modifier and no second control. Arrows step ONE step, ten with Shift; the other way round jumped a 0.5 dB trim by 5 dB on the first press, which reads as the key having done something else entirely.

- **FOCUS — THE SHIPPING TARGETING MODEL (`src/audio/resonanceFocus.js`). Zones are what it replaced, still reachable with `?resoTargeting=zones` or the localStorage key.** The flag survives the promotion rather than being deleted with the loser, for the reason `voicerxBaseline` keeps its: the decision rested on working a file in one model and then the other, and that is the only way back to the comparison — or to a patch built under zones — without a rebuild. **⚠ THE "NOT SHIPPED" BADGE MOVED TO THE OTHER MODEL**: an override is a thing you forget you turned on, so the one that is not the default is the one that announces itself, and it is now zones. Zones give a straightforward mental model — select a zone, set its parameters — and are unwieldy in use: the whole spectrum has to be partitioned and every partition tuned before the panel means anything, contiguous zones can differ abruptly, and a resonance spanning a boundary is half treated. Focus replaces the partition with **one global detector plus a sparse overlay of nodes that BIAS THE THRESHOLD**, `selectivity[k] = clamp(global.selectivity − bias(f_k))`, where `bias` is a sum of Gaussians in log frequency. **Not shipped, not listened to** — the flag exists because no corpus can say which model a person can think in.
  - **THE OFFSET IS THE WHOLE ARGUMENT, AND IT ANSWERS "OVERRIDE OR ADDITIVE?" BY MAKING THE QUESTION UNASKABLE.** A zone's settings are ABSOLUTE, so there is no "no opinion" value: a zone carrying selectivity 20 is not saying "leave this alone", it is saying twenty, and it says it whether or not anyone chose it. That is why the whole spectrum must be set up. An offset has a true zero, so an untouched spectrum is genuinely untouched and the default panel is just the global knobs. And a node carrying `−8 dB` cannot be read as an override of `20` — they are visibly different quantities. The panel prints the sum (`THRESH 6.9 = 20 − 13.1`) at the node's own frequency, so the rule is on screen rather than in a tooltip.
  - **⚠ THE SIGN IS THE OPPOSITE OF THE ARITHMETIC AND IT IS ASSERTED DIRECTLY.** Selectivity is a threshold and runs backwards — higher means less is cut — so an amount stated the way a person thinks about it ("work harder here") must be SUBTRACTED. Backwards, every knob still turns and every curve still draws and the control does the reverse of its label; nothing downstream catches it. `±18 dB` is derived rather than chosen: it is exactly what one node needs to reach either end of the selectivity range from the stock 20, so "work as hard as you can" and "leave this completely alone" are both sayable and nothing past it does anything.
  - **A NODE BIASES ONLY THE THRESHOLD, and that is what keeps it to three numbers.** Reduction is proportional to excess over threshold, so lowering it in a band catches resonances that were being missed AND deepens the cuts already landing — one number covers "work harder here" monotonically. A node with five fields is a zone with extra steps.
  - **⚠ WHAT IT GIVES UP, MEASURED AS A DESIGN COST RATHER THAN HIDDEN: A PER-BAND CEILING.** A bias cannot express "at most 6 dB here", and the honest ceiling differs by band — 12 dB in the low mids is fine, the same 12 dB on sibilance is a lisp. `maxCut` is global here. If listening misses it the answer is an optional fourth node field, not a return to absolute per-band values.
  - **SHARPNESS STAYS GLOBAL, and the conceptual and the mechanical reasons agree.** Sharpness says WHAT SHAPE counts as a resonance (a property of the detector); a node's **Width** says WHERE you are paying attention (a property of the map). Different axes, which is what stops the panel having to explain "node Q versus sharpness" — the question that sinks every node-style suppressor. It is also the kernel's `uniform` fast path: each distinct sharpness costs one more inverse FFT per frame, so one value means one envelope ALWAYS, and the bit-identical guarantee that zones hold only on an untouched panel holds here permanently. The label is **Width**, never Q, and it is drawn as a shaded span rather than a bell.
  - **HARMONIC PROTECTION BECOMES GLOBAL WITH A CEILING, losing nothing measured.** The per-zone flag existed because the mask blocks 67–88% of every octave — real protection where partials are widely spaced, a blanket veto where sibilance lives — so "protect the fundamental region, work freely above 5 kHz" was the setting the effect most wanted. That is a statement about a FREQUENCY, and one ceiling says it directly on every file, where a per-zone flag says it only if the zones happen to be well placed. Crossfaded over the same 1/6 octave a zone boundary uses, for the same reason.
  - **THE KERNEL DID NOT CHANGE — one dispatch line.** `buildResonanceFocusCurves` returns exactly the shape `buildResonanceZoneCurves` returns, because the detector loop, the envelope groups, the mask and the ceiling all read per-bin arrays and none of them knows which model drew them. **A focus patch with no nodes is bit-identical to the stock zone patch**, curve for curve, so switching models on an untouched file changes nothing and an A/B is of the TARGETING rather than of two tunings (`RESONANCE_FOCUS_GLOBAL` is `ZONE_STOCK`, carried over unchanged and carrying its caveats with it).
  - **THE NODES LIVE IN THE PLOT, ON A CURVE FLOATING OVER THE SPECTRUM — THERE IS NO RAIL.** It shipped first as a separate 58 px strip under the display, with a 44 px plate row for the selected node's numbers, and both were rejected on sight: 102 px of instrumentation beside the picture it describes, when the thing it targets is *in* that picture. Two intermediate designs were drawn and also rejected for the same reason — an inset lane inside the plate, and the same lane plus tethers — because moving a rail indoors is still a rail. What ships is one curve over the material, its handles on it, and the selected node's three numbers on a pill at its own handle.
  - **⚠ THE HANDLES CANNOT RIDE THE THRESHOLD LINE, AND THAT IS MEASURED RATHER THAN ASSERTED.** The obvious reading of "put it over the spectrum" is to hang them on the threshold staircase, since that is the line a node actually biases. The spectrum band is 70 dB over ~139 px, so 1 dB is ~2 px, and a per-bin envelope swings tens of dB between a vowel and a pause: on a ±12 dB syllabic probe — conservative against real speech — **the threshold line at one node's frequency travels 43 px in two seconds and up to 7 px between consecutive frames**. That is the discarded Gaussian nodes' "impossible to aim" report in numbers, and it is why the curve keeps the threshold's PLACE and not its MOTION — a static datum, with nothing moving unless a knob does.
  - **⚠ IT RUNS THE FULL WIDTH, CONTINUOUSLY — AND THE ARGUMENT AGAINST THAT WAS OVERRULED BY LOOKING AT IT.** The argument was real: a bias is flat almost everywhere, so an edge-to-edge stroke paints a full-width horizontal line, and a full-width horizontal line is a rail. It shipped broken at **0.3 dB** on that reasoning, the same figure the reduction trace uses. Rejected on sight — over the spectrum, with no plate, no band and no reserved row, a full-width line reads as a floating line ON the display rather than as an independent display area. **Being technically a rail is not the same as reading as one**, and only rendering it settles which. What the break cost was continuity: the curve appeared and vanished as a node was dragged past the threshold, and with several nodes it broke into pieces that looked like separate objects rather than one adjustable line. `BIAS_VISIBLE_DB` and `biasRuns` are deleted rather than left unused.
  - **⚠ AND THE BREAK WAS NOT ASKED FOR — it was substituted for a decision that had already been made.** The choice between the treatments was explicitly "technically still a rail, but it reads as a floating line over the main display rather than an independent display area". Re-deciding that as a "refinement" is the failure worth recording here, not the pixels: a preference of mine dressed as an improvement to someone else's settled call.
  - **`FOCUS_DATUM_FRAC` AND `FOCUS_HALF_SPAN_FRAC` ARE FIXED BY A CONSTRAINT, NOT BY TASTE: the curve must not escape the spectrum band.** Above it is the reduction lane and below it the FOUND strip, both measuring something else, and a curve drawn over either is the two-lane confusion this plot was already undone for once. Datum at 0.22 of the band down from its top, full travel 0.20 either way, so the curve lives in [0.02, 0.42] of the band. At the shipping height that is **1.54 px/dB against the deleted rail's 1.61** — within 5%, so the drag feels the same after moving house.
  - **⚠ POSITIVE BIAS DRAWS DOWNWARD.** More cut lowers the threshold toward the material, and on this plot down IS toward the material — the spectrum is below and the reduction trace already hangs downward for "more". A curve rising for "more cut" would be the only thing on the plate running the other way, and nothing downstream would catch it. Pinned, along with the matching arrow-key sense.
  - **⚠ THE WHEEL BINDING WAS DEAD SINCE BEFORE ANY OF THIS — `@wheel.prevent="onWheel"` with no such function defined anywhere in the file.** Found while wiring the width gesture. **Two guesses about the failure mode were wrong before measuring it in a browser**: it does not throw, and Vue does not drop the binding either. It applies the modifier and calls nothing, so wheeling over the plot **silently swallowed the page scroll and did nothing with it** — in a window that already prints `MORE ↓` when it runs past the fold. The `.prevent` had to go as well as the missing handler, since a template modifier is applied before the handler runs and no early return can give the scroll back.
  - **⚠ DELETING THE RAIL DELETED THE ONLY ACCESSIBLE DESCRIPTION OF THE NODES.** The rail component carried its own `aria-label`; the plot's named the zones and the resonances and never mentioned a node. With the plate row gone too, a node's frequency, width and amount now exist **nowhere else on the panel**, so the plot's accessible name lists them and `FOCUS_HINT` replaces `ZONE_HINT` in that mode. Caught by driving the real component in a browser, not by reading it.
  - **⚠ THE TWO RESERVED BANDS ARE SWAPPED: FOUND AT THE TOP, REMOVED AT THE FLOOR.** Reading the plate top to bottom now runs cause, material, effect, and the material sits between the two things that describe it rather than under both. It also gives the focus curve clean air — its datum sits near the top of the spectrum band, which had it immediately under the reduction lane, the two busiest elements on the plate and one of them a control surface, in the same few dozen pixels. **It does not violate the recorded reason for the strip's old place**: that note is that the held shape needs "a baseline that cannot move", and the plate's top edge is as immovable as its floor; the separate note about a strip colliding with crossings is about an UNRESERVED row, and this is still a reserved band.
  - **⚠ THE PEAK HOLD WAS LEFT AT THE PLATE'S TOP EDGE BY THE SWAP, AND MY SWEEP FOR IT WAS THE WRONG SWEEP.** Everything else in the lane was offset by grepping for `reductionH.value`; the hold reads the local alias — `peakBins[d] * h` — so the grep walked straight past it and the trace went on being drawn from y = 0. It was reported as a stray trace left over from the old layout, which is exactly what it looked like. **⚠ It is NOT vestigial** — it is the reduction's own peak hold, the thing that makes an intermittent ring findable — so it was moved into the lane rather than deleted. A grep for one spelling of a quantity is not a sweep for the quantity.
  - **⚠ EVERYTHING THAT LIVES IN THE REDUCTION LANE HAD TO MOVE WITH IT — including `markAt`, which is the one that fails silently.** The rail, the trace, the peak hold, the grid horizontals, the GR numerals and the marks all offset by `reductionTop`; the hit test is the one that produces "dots that cannot be clicked where they are drawn", which this component's own notes call out and which no test would have caught. Verified in a browser by probing down the lane for the click that actually selects the deepest mark, rather than by re-reading the arithmetic.
  - **THE REMOVED LANE INKS THE COMPLEMENT — the lane is a mass and the cuts are bitten out of it.** Chosen by eye against the two alternatives (the old fill between rail and curve, and the silhouette mirrored to grow upward). The mirrored one was rejected on a stated ground rather than taste: **the focus curve two bands up already means "down is more cut"**, so a trace growing upward for the same idea would put two opposite conventions on one plate. **⚠ What the complement costs is that ink means something different here from everywhere else on the plate** — the focus curve's fill is the bias and the FOUND strip's fill is a crossing, both ACTIVITY, where this one is what SURVIVED. Anchoring the mass at the floor and fading it upward is what keeps that from reading as a measurement; **the case that settles it is the IDLE lane**, which under this scheme is a full slab, and reads as ground rather than as a bright block only because of that gradient. The worked patch cannot show that case, which is why it was rendered on its own.
  - **⚠ THE CURVE'S TWO AXIS LABELS SIT ON A BACKING, because the threshold staircase runs THROUGH them.** Both are at the left edge, which is exactly where the reference is lowest on speech, so the dotted line descends across "MORE CUT" and cuts the glyphs in half. The two are drawn by different functions and neither looks wrong on its own — only rendering it shows the collision.
  - **THE BANDS COLLAPSE WHEN THEIR OVERLAY IS OFF, so the spectrum takes the space back.** The plot tiles three bands — reduction 35%, FOUND 13%, spectrum the rest — and it tiled them at fixed fractions whatever was showing, so switching REMOVED off left a third of the plot empty and the spectrum no larger. Reported as the display feeling cramped, and it was: on a 280 px plot, turning both off hands the spectrum **128 px back**, nearly doubling it. A conditional fraction rather than a second set of constants — the trace, the marks, the GR scale, the strip and the focus curve's datum all read the same two numbers, so one change moves them together and there is no parallel "collapsed" geometry to drift.
  - **A NODE HAS A DELTA, AND IT IS THE ZONE DELTA'S INTENT RATHER THAN ITS TRANSFORM.** The zone version isolated a BAND — every other zone switched off — and a node is not a band, so it cannot be copied literally. What carries over is the question: a zone delta answered "what is being taken out HERE", and a node has a "here" of its own, its own influence. So the threshold is crossfaded between what the patch really does and OFF by the soloed node's own weight, `selectivity = effective·w + max·(1 − w)`. Inside its reach you hear exactly what the full patch does there; outside, nothing is touched. **It needs no special case for shape** — a shelf solos its whole shelf — **and none for a node at amount zero**, because the WEIGHT carries the region where the bias would not.
  - **⚠ ASKING IT OF A BYPASSED NODE IS NOT SILENCE, which is the one place it differs from the zone delta.** A bypassed ZONE removed nothing, so soloing it was honestly silent; a bypassed NODE only means "no opinion here", and the global detector is still working that region — so what comes out is what the region is losing anyway. That is the true answer to the question being asked, and the more useful one.
  - **⚠ IT IS THE MORE DANGEROUS OF THE PANEL'S TWO MONITORS, for the reason the zone delta was.** The delta monitor itself is expressible only inside the kernel; the ISOLATION it rides on is an ordinary parameter (`focus.solo`), so nothing about it would look wrong if it leaked into what Apply renders — it would simply write a one-node pass into the timeline. `liveFocus()` applies it on the way to the live kernel only and `currentParams()` never consults it, pinned by reading the source in `test/ui/resonanceFocusSolo.test.js`. The plot draws the veil over everything outside the soloed region, because a display that did not show it would disagree with the speakers.
  - **A NODE HAS A SHAPE NOW — BELL, LOW SHELF, HIGH SHELF — and a shelf says what no bell can at any width.** "Work harder on everything above 5 kHz" is a shelf; a wide bell aimed at the same place falls away on both sides and lifts the midrange on its way past. **⚠ A SHELF IS A WEIGHT, NOT A SECOND MECHANISM**: every shape returns a number in [0, 1] that the amount is multiplied by, so the sum, the clamp, the curve and the solo window are all shape-blind. `SHELF_K` is set so a shelf is at 5% half a span below its corner and 95% half a span above, which makes `spanOct` mean the same kind of thing on both shapes. An unrecognised shape falls back to a bell rather than producing a fourth behaviour, and the stock patch is unmoved by shapes existing.
  - **THE NODE CARD IS A FLOATING HTML PANEL ON THE PLOT, opened by clicking a node.** Frequency, width and amount as typeable fields, plus shape, delta, bypass and delete. **⚠ IT EXISTS BECAUSE WIDTH HAD ONLY A WHEEL**, which is a poor control on a trackpad and no control at all by keyboard or touch. HTML rather than canvas is the point — real inputs bring focus, selection, typing, tab order and a screen reader's understanding of a spin button for free. It floats and closes again rather than sitting under the plot, which is what stops the panel's chrome growing back. It is hosted INSIDE `ResonanceSpectrum` because it is placed from the node's pixel coordinates, and a card hosted by the panel would need the plot to publish its geometry — a second copy of the mapping, which this component has already recorded the cost of. **The canvas pill is suppressed while the card is open**, or the same three numbers are printed twice with the card over one of them.
  - **`DeviceField` WHEELS NOW, AND ITS FREQUENCY FIELDS ARE LOGARITHMIC — the second was the real defect.** The control was a drag or a typed number, which covers a mouse and a keyboard and leaves a trackpad with the worst of both. Adding the wheel exposed the larger fault: over 20 Hz–20 kHz the LINEAR drag is **133 Hz per pixel**, so one pixel at the bottom of the range jumps 200 Hz to 333, and a 1 Hz wheel notch does not move the readout at all — 3180 to 3181 still prints "3.18k". Both were true before anything wheeled; the field was fine for a ceiling in dB and quietly useless for a frequency. `log` maps drag, wheel and arrows through one 0..1 position, with a notch of **one semitone** — the same unit the plot's arrow keys move a node by. **The linear path is arithmetically identical**, so nothing that does not opt in moved by a bit.
  - **⚠ THE SOLO IS RECONCILED BY THE NODE'S `id`, NOT BY ITS INDEX.** Reported from use: deleting a node left the delta monitor on, auditioning whatever node had shifted into that slot — or nothing at all, with the panel still lit. Every edit replaces the array, so an index survives a deletion happily and silently means something else afterwards. `syncFocus` re-finds the id on every edit and clears the solo when it is gone, which covers deletion, reordering and replacement with one rule. **The reconcile lives there rather than in the gestures** because every route that can invalidate a solo — the card's DELETE, the plot's double-click, the keyboard's Delete — arrives through that one function, and a rule applied per gesture is a rule with a gesture missing from it.
  - **NODES ARE NUMBERED LEFT TO RIGHT, AND THE ARRAY IS STILL NOT SORTED.** They are stored in the order they were added, so the array index numbered them by AGE — the third node placed read "3 OF 4" wherever it sat, which is no help in finding it. ⚠ Sorting the array is the wrong fix: selection, solo and the drag in progress are all indices into it, and re-sorting on a frequency change would renumber them **under a drag**, which is the one moment an index has to hold still. So the order is a VIEW — `focusRanks` for what the card prints and the accessible name lists, `focusNeighbour` for what the arrow keys walk. - **RUMBLE IS ITS OWN HEURISTIC, outside the region/deviation structure** (`src/audio/voicerx/rumble.js`). Reported from use: VoiceRx almost never cuts the low end. It doesn't, and `sub_bass` fails there **four ways at once** — the analysed span starts at 60 Hz, exactly its scan floor, so its left context window is off the end of the spectrum; at `N_FFT` 4096 that scan is **6.5 FFT bins** wide and its context 1.3 (against `nasal`'s 51); it carries the **highest threshold in the table** at 4.0 dB; and real rumble is mostly **below 60 Hz**, which the envelope never looks at. Measured: a +20 dB resonance at 90 Hz moves its deviation 1.12 → 2.83 dB and never fires; +20 dB at 40 Hz moves it **0.06 dB**. No threshold tuning fixes a measurement taken from six bins with one anchor. **Note the same structural flaw at the other end** — `REGION_SPAN_HZ` is exactly the union of the scan ranges with no margin, so `air` has no right anchor either, and that is the region whose +6 dB boosts at 14.8–16 kHz the slope guard had to suppress. One cause, opposite symptoms.
- **How the rumble heuristic works, and what it rests on.** Below F0 there cannot be voice — physics, not a comparison — so it asks a different question entirely and never touches the cepstral envelope. **Corner is prophylactic, depth is measured.** The corner is `clamp(min(0.75 × p25F0, 0.55 × medianF0), 40, 100)`; *not* a low percentile of F0, which is the obvious choice and is wrong — the tracker's search floor is 70 Hz and octave-halving errors pile against it (reference clip: p1 71, p5 76, p10 84, p25 107, median 138, so p5 reports the floor rather than the speaker). Depth comes from the **tilt of the spectrum below the corner**: a clean recording falls away toward DC because nothing is down there, rumble is energy piled at the bottom and flattens it. An absolute energy ratio was tried first and fails — 20 dB of rumble moved it 5.5 dB, and a 90 Hz resonance *above* the corner moved it the same way. Tilt on the reference clip: clean −14.7, +6 dB rumble −11.1, +12 −7.4, +20 −3.2, and a 90 Hz peak −20.3 (correctly ignored). Gain is the excess over a clean tilt, capped at 12 dB, suppressed below 1 dB. It reads the **whole selection including pauses** — HVAC does not stop when the narrator does. `sub_bass` is dropped from the correction set (`skipReason: 'rumble_heuristic'`) so two mechanisms cannot both place a shelf down there. **All three detector baselines are bit-identical after this** — independent confirmation that `sub_bass` never contributed a band.
- **THE RUMBLE MEASUREMENT HAS ITS OWN 16384-SAMPLE WINDOW, and running it on the region machinery's 2048 was a defect with two symptoms** — both found by pointing it at real recordings for the first time. **(1) It returned null, producing no rumble finding at all, on low corners.** The tilt bands are fractions of the corner, so at 2048 they held one or two bins, and below two bins `bandLevelDb` bailed and took `analyzeRumble` with it. Swept 40–100 Hz: at **48 kHz every corner below 75 failed**; at 44.1 kHz every corner below 65 failed, and 75 failed while 70 and 80 passed — bin-alignment luck. A clean synthetic voice at F0 90 returned null outright, so **deep-voiced narrators got no rumble analysis and nothing said so**. That is the same too-few-bins failure this heuristic was written to *replace* in `sub_bass`, whose 6.5 bins its own header criticises. **(2) Leakage worth 8 dB and a sign.** At 48 kHz a 2048 frame gives 23.4 Hz resolution and a ~94 Hz Hann mainlobe, so the whole 20–100 Hz region sat inside one mainlobe and the HIGH band, nearest F0, caught the most — every tilt read steeper than it was. Three real narrators at frames 2048 / 8192 / 32768: **−3.28 → +4.47 → +5.00** (sign flips; that file's spectrum genuinely *rises* toward DC), −3.43 → −3.87 → −3.90, −9.57 → −8.23 → −8.35. **Measured cost: 544 ms → 307 ms** on a 35.5 s selection — the fix is 56% of the old price, because a 16384-point FFT every 4096 samples is less work than a 4096-point one every 512.
- **`CLEAN_TILT_DB` moved −14 → −5 with it, and the two are not separable.** Correcting the leakage shifts every tilt flatter, so the old value began offering **8.8 dB of cut on clean audio** the moment the window was fixed. **⚠ It is still not really a constant**: clean synthetic voices measure tilt −20.10 / −9.49 / −10.27 / −5.20 at F0 90 / 120 / 180 / 220 — a 15 dB spread across recordings with nothing wrong. Any single number therefore trades false positives against misses, and −5 is chosen as the **flattest clean reading**, so nothing measured as clean can be offered a cut. Swept: worst false positive 0.00 dB at −5, 0.80 (not reportable) at −6, 1.80 at −7, **8.80 at the old −14**; detection on −30 dBFS of synthetic rumble is 3.0 dB at −5. A knee, not a point on a slope. **The cost is misses, which is the right way round for a tool that runs unasked.**
- **On the three real files the fix changes the answer for the better:** −9.91 dB (40–60 Hz sits 7.9 dB under its own speech band — heavy rumble, correctly cut), −1.06 dB (raw, −11.5 dB), and **0.00, suppressed** on the hard-mastered file that was already high-passed. Before the fix all three were offered cuts: −10.72 / −10.57 / −4.43.
- **⚠ Still no known-clean unmastered narrator recording.** The flattest clean reading is synthetic; the one real file with a clean bottom end is hard-mastered, so using it as the clean reference assumes what it is meant to prove. **The remaining work is defect (2) proper**: make the clean tilt a function of the corner, or decide tilt is the wrong statistic and measure sub-F0 energy against the noise floor instead.
- **The rumble heuristic cannot be scored by the synthetic corpus, and the reason is a corpus defect.** `synthVoice` gates its pauses with a hard on/off, and those discontinuities splatter broadband energy below F0 that no real recording has: the synth's sub-F0 tilt reads **−1.4 dB** where a real clip reads −14.7, so the heuristic sees rumble that is purely a generator artefact. Rumble bands are therefore excluded from `runScorecard` (they are also unclaimable — no planted defect can match a band justified by physics rather than by deviation), and `test/dsp/voicerxRumble.test.js` builds its own signals with **raised-cosine pause edges**. **`CLEAN_TILT_DB` was calibrated on one file** and was the first thing to re-derive once raw, unmastered narrator recordings existed — every file available when it was written was synthetic or already mastered, and mastering has usually high-passed the bottom away already. ⚠ **It has since moved to −5 alongside the window fix; the −14 quoted in this bullet's history is not the shipped value.** **Sixth time this corpus has been too clean to answer the question asked of it.**
- **`MAX_TOTAL_CAP_FACTOR` IS 1 — the per-region dB caps are TOTAL caps.** `MAX_CUT_DB = 6` for mud now means this tool will never cut mud by more than 6 dB, which is what the number reads as. It was 2, on the argument that holding the total to the per-pass figure would make iterating pointless. That argument was wrong about what iterating is *for*: iteration does not exist to keep spending on a region already at its limit, it exists because **a second feature can be unmeasurable until a larger adjacent one comes down**. That still works at 1 — a region first detected on a later pass gets its own full budget. Reproduced synthetically and pinned: a 900 Hz +10 dB hump beside a 550 Hz +8 dB one hides the smaller entirely until the first correction lands, and `boxy_honky` is then detected **on pass 2**. Same mechanism as the reference clip's mud band. **Measured cost: recovery median 0.50 → 0.42** on the chord (0.44 → 0.42 on the trend) — large defects are now deliberately under-corrected and stay flagged rather than earning a big surgical cut taken on trust. Detection and invented bands are unchanged.
- **THE CHORD'S OVERSHOOT WAS THE THIRD ITERATION PASS — fixed, `MAX_CORRECTION_PASSES` 3 → 2.** Reported from listening: the chord cuts harder than the defect warrants. It does, and the mechanism is that each pass re-derives its baseline from audio the previous pass already altered, so a reference carrying any bias compounds that bias every round. The original argument for three passes was pure convergence arithmetic and assumed each pass re-measures the *same* defect more accurately; it does not. **Detection is 67% at one, two and three passes** — iteration never finds a defect, it only decides how much to spend on one already found — so capping it costs nothing measurable. On the 5 kHz-notch clip the chord goes from **−7.9 dB to −5.7 dB** on a region it measured at 5.12 dB, keeping both bands (340 Hz −2.0 and 609 Hz −5.7; with `MAX_TOTAL_CAP_FACTOR` since taken to 1 it lands at −5.0, the region's cap); corpus invented gain 79.4 → 75.7 dB with detection and recovery unchanged. **One pass is too few** — recovery 0.50 → 0.42 and the mud band vanishes, because it is only measurable once the larger adjacent hump comes down, which is the legitimate half of iterating. The shipping trend is near-indifferent (19.8 → 18.7 dB, detection and recovery identical), which is the same tell as its 0.00 convergence residual: a reference not chasing its own corrections has little to do on a third round.
- **Listening prefers the chord's two-band answer on the notch clip, and that is a real signal about band merging, not only about baselines.** The chord reports `mud 340 Hz −2.0` and `boxy_honky 609 Hz −5.7`; the trend at `thresholdScale 0.8` detects **both regions too** (mud 2.07 dB @ 410, boxy 2.46 dB @ 445) but places their centres 0.12 octaves apart, so `mergeBands` (`MERGE_OCTAVES = 0.33`) collapses them into one band at 427 Hz. So the disagreement heard as "the trend misses the boxiness" is partly **the trend locating the boxy peak 0.45 octaves lower than the chord does**, and then merging. Where each reference puts a peak inside a wide scan region is unexamined and is the next thing to measure.
- **LISTENING SAYS THE THRESHOLDS ARE MISCALIBRATED FOR THE TREND, and the corpus agrees.** Reported from real use: the chord catches critical defects the trend walks past, *and* overshoots — big cuts where a smaller one was right. Both halves have a mechanism, and they are the same mechanism. Every threshold in `regions.js` was tuned against **chord** deviations, which are inflated by the curvature bias (a convex spectrum sits above its own chord whether or not anything is wrong), so each threshold silently absorbed some bias; remove the bias and the same numbers are too high. On the original 5 kHz-notch clip the trend measures a real boxy resonance at **2.46 dB against a 2.5 dB threshold** — a miss by 0.04 dB on a defect a person can hear — while the chord calls the same region 5.12 dB and, over three passes, spends **−7.9 dB** on it (a single pass at `SCALE = 0.70` would spend −3.6). That is the overshoot: iteration compounding on an inflated measurement. Scaling every threshold by **0.80** beats *both* shipping detectors on every synthetic axis at once — detection **70%** (chord 67%, trend 63%), recovery **0.58** (0.50 / 0.44), invented bands **7** (24 / 5), invented gain **27.1 dB** (79.4 / 19.8) — with convergence still 0 and risky boosts still 0. Below 0.75 it collapses (x0.60 → 41 invented bands), so 0.80 is a knee, not a slope. On the clip it finds the low-mid problem the chord found, at **−3.2 dB total instead of −7.9**. **It is NOT the default**: that table is the synthetic corpus, which has been wrong about the real-audio ranking three times, and lowering a detection threshold can only increase what gets offered on audio that needs nothing. Reachable as `?voicerxThreshold=0.8` (or `analyzeVoiceRx(..., { thresholdScale })`) so it can be heard; **run `npm run scorecard:real` before promoting it.**
- **VoiceRx is measured, and the numbers are poor.** `npm run scorecard` runs a 58-case synthetic corpus (`test/voicerx/`) in which a clean voice is corrupted with a *known* EQ move, so the correct output is the exact inverse and needs no human judgement. Baselines in `test/voicerx/baseline.json`. **`current` (trend): detection 63%, recovery median 0.44, spread 0.37, 5 invented bands totalling 19.8 dB, aim 0.011 octaves.** `v1chord` (now `current`): detection 67%, recovery 0.50, spread 0.58, **24 invented bands totalling 79.4 dB**, aim 0.021. Note what the switch bought and cost on synthetics alone: 4 points of detection for a **79% cut in invented gain** — and the synthetic corpus is the one that *disagrees* with the real one about this trade, see the real-corpus table below. Aim is the one strong result on both. Where the trend still invents: the **bandwidth family, 3 bands / 15 dB** (cuts at ~9 kHz on band-limited files — the trend's own edge weakness, distinct from the boost family the slope guard fixed), where the chord invents none. Blind spots are structural: `body_warmth`, `lower_presence` and `air` are dip-only with `MAX_CUT_DB = 0`, so a hump anywhere in 1200–2500 Hz (or at 180 Hz, or 11 kHz) is **undetectable by construction**. The trend adds one of its own, **measured and pinned in `voicerxAnalysis.test.js`**: a defect sitting on the spectrum's own maximum is near-invisible to a smooth local reference, so a 12 dB resonance at 300 Hz on an F0 120 voice reads 1.24 dB against the trend where the chord saw it clearly. That is the mechanism behind the low-frequency misses (180/200/220/300/400 Hz) and it is inherent to the approach, not tunable. `test/voicerx/scorecard.test.js` pins a 6-case subset as a regression guard — it asserts the numbers are *unchanged*, not that they are good; re-record with `node scripts/voicerx-scorecard.mjs --smoke --write-baseline`.
- **VoiceRx v2 exists, behind the harness, not wired into the app** (`src/audio/voicerx/v2/`; its `robustTrend` and `toLogGrid` now live one level up in `voicerx/trend.js` because the shipping detector uses them). Measure (envelope + two half-envelopes + noise floor) → mask (per-frequency **measured SNR**, replacing `DEAD_REGION_DB`/`no_energy`/`flatBaseline`) → robust local quadratic trend (replacing the chord) → continuous peak/trough finding on the residual (replacing the nine-region grid, `mergeBands`, and the directional blind spots) → confidence from four multiplied terms (evidence, conditioning, split-half stability, plausibility — replacing the caps and the hole guard) → `gain = -height × confidence`. **63 hand-set region constants become 6.** Scored on the same corpus: detection **67%→83%**, recovery median **0.50→0.67**, spread **0.58→0.41**, invented bands **27→4**, invented gain **90.1→7.7 dB**, aim **0.021→0.015** octaves. Score both with `npm run scorecard --detector=v2`; both are pinned in the baselines.
- **v2 output policy (step 3).** Continuous detection finds everything, including real fine structure that is not a tonal defect. Three rules shape the output, each measured: a **minimum feature width of 0.22 octave** (below a critical band the ear does not hear a peak as tonal colour — the junk bands on the reference clip measured 0.042–0.125 octave, the planted defects 0.25–0.63); a **minimum spacing of 0.33 octave** between corrections, greedy by strength, which is what killed the adjacent opposite-sign pairs; and a **cap of 6 bands** (a product limit, not a DSP one). Advisories get the same spacing rule, or one wide notch reports itself two or three times. Reference clip: **6 sensible bands + 1 correct hole advisory**, down from 10 bands.
- **THE REAL CORPUS CONTRADICTS THE SYNTHETIC ONE, and the real one wins.** On 13 commercially mastered ACX files (31 windows), where the right answer is very nearly "no correction": v1 offers bands on **30/31 windows, 3.06 per window, 336.6 dB total**; v2 offers **30/31, 3.35 per window, 388.8 dB**. The synthetic corpus rates v2 at 4 invented bands across 58 cases; real finished audio gives ~104 across 31 windows. **The synthetic ranking does not transfer**, and on the metric that matters most for a consumer tool — do not damage good audio — neither detector is fit to ship, with v2 marginally worse by count. Two specific, addressed bugs fell out (below). Do not read the synthetic scorecard as a shipping signal again without checking it against `npm run scorecard:real`.
- **The SNR mask looked inert, and that reading was itself the epsilon bug.** It first measured **100% live on 31/31 real windows**, never excluding anything, and I wrote it off as a mask that is not a mask. Wrong diagnosis: the absolute log-power floor was flattening the *noise* envelope to a constant, so every SNR ratio was measured against a floor that could not go below the epsilon and came out enormous. With the relative floor in place the same corpus reads **40% live to 539 Hz on `bk_ParadeofHorribles`** (SNR 9.9 dB, the file whose pauses are literal digital silence at −240 dBFS), **94–95% live to 11.2–12.2 kHz on two `ProjectHailMary` windows**, and a median speech-band SNR of **48 dB rather than 55.4**. The mask now excludes bandwidth edges and refuses spectrum it cannot measure — on `ParadeofHorribles` that alone takes v2 from 4 bands to 1. It still does **not** exclude sub-F0, so the fundamental bug below stands on its own.
- **v2 cuts the fundamental.** In 17 of 31 real windows v2's lowest band lands within 7.5% of the measured F0 — ratios 0.93 to 1.075, across seven different narrators — and up to −8 dB. F0 is the voice's pitch, not a defect in it. The mechanism is structural: below F0 there is no voice energy at all, the envelope steps up into it, and a smooth quadratic over ±2.5 octaves cannot follow a step, so the envelope sits above the trend at F0 and reads as a resonance. The SNR mask should have excluded sub-F0 bins and does not. `nearF0` in the real-corpus report flags it per band. Measured: **v2 17/96 bands within 15% of F0, v1 1/89** — and the epsilon fix, which repaired the mask everywhere else, moved this count by exactly zero — and v1's single case (ProjectHailMary, F0 105.3, band at 94 Hz −8.0) is the one narrator whose F0 falls in `sub_bass`, the only low region v1 scans for humps. **v1 is protected by its directional blind spot, not by better measurement**: for F0 between ~135 and 280 Hz the fundamental lands in `body_warmth`, which is dip-only with `MAX_CUT_DB = 0`, so v1 cannot cut there whatever it measures. Reproducible synthetically — a clean F0 160 voice gives a 1.29 dB residual bump at F0 (under the 2 dB floor, which is why 58 synthetic cases never showed it), and adding the 60–80 Hz high-pass every ACX master carries takes it to 2.2–2.6 dB and v2 emits a band. **Removing a constraint you do not fully understand means inheriting what it was suppressing.**
- **Two thirds of what v2 says on real audio comes from two addressable bugs.** Half-octave histogram of its 104 invented bands: **177 Hz — 16 bands** (the F0 bug) and **11.3 kHz — 12 bands**, together 27% of everything it emits. v1's own cluster was **16 kHz — 6 bands, every one a +6.0 dB boost pinned at 2× its cap**, the worst possible direction there (boosting 16 kHz raises hiss) — **fixed by the slope guard, that bin is now empty**; v2's two are not, it does not use that code path. v2 also emits a run of **+3 to +5 dB boosts at 4–6 kHz** across many files: mastered audiobooks are de-essed there, so v2 is systematically offering to undo professional de-essing — the direct consequence of a notch reading as a deficiency.
- **Repeatability, measured: v1 74%, v2 50%.** Of the bands a detector reports on one window of a finished file, that fraction recurs in every other window of the same file. v2 tells you something different half the time you ask.
- **How the trend was isolated before it was adopted (`v1trend`, now `current`).** v1's region tables, directions, thresholds, caps, SCALE, iteration and merge unchanged; only the chord baseline replaced by the robust local quadratic. Synthetic corpus: invented bands **27→8**, invented gain **90.1→29.8 dB**, and the **notch family goes to zero** phantom corrections — the failure that started this investigation, gone without a hole detector involved. It costs detection (67%→63%, recovery 0.50→0.44) because v1's thresholds were calibrated against chord deviations and the trend is a tighter reference; that recalibration is deliberately not done against synthetics. **It does NOT fix the bandwidth-edge boosts** — that bug lives in the region structure, not the baseline (the slope guard does, and covers all three detectors' v1-path regions).
- **The two corpora disagree about the trend, and the real one decided it.** Same 13 files, 31 windows, with the slope guard in place:

  | on finished masters | v1 | `v1trend` | v2 |
  |---|---|---|---|
  | windows offered bands | 30/31 | **26/31** | 30/31 |
  | bands per window | 2.87 | **1.55** | 3.10 |

  (v2's column is post-epsilon-fix; v1 and `v1trend` are unmoved by it, bit-identical before and after on all 31 windows.)

  `v1trend` invents **half** of what v1 does and **45%** of what v2 does, at a third of v2's total gain, and never touches the fundamental. The synthetic corpus charged it 4 points of detection for the trend; the real corpus refunds that many times over on the axis that matters for a consumer tool. **Its one real cost is repeatability, 75%→56%** — and part of that is arithmetic (at 1.55 bands per window a single non-recurring band costs proportionally more than at 2.87), so a like-for-like recount is the one number to pin down before adopting it (the tooling for that is now in place — see the repeatability note below). v2 is unchanged by the guard, as expected — different code path.
- **The notch advisory fires on 9 of 13 finished masters**, 6–15 dB, at 5.6–10.3 kHz and clustered at 6–8 kHz in eight of the nine, identically for v1 and `v1trend` (the hole detector is baseline-independent). These are most likely *real* — professional de-essing cuts exactly there, so each instance may well be a true positive. That does not save it: **an advisory that fires on 70% of professionally finished audio carries no information**, whatever its per-case accuracy. Before this ships to users it needs either a de-essing-shaped exclusion or a much higher bar in that octave.
- **v2's top-end failure was mostly the epsilon, and is mostly gone.** It scored zero bandwidth-spurious bands on synthetics but on real audio emitted a 12-band cluster at 11.3 kHz plus 2 at 16 kHz, and reported suppressed "resonances" of **19.8–23.4 dB at 11.3–15.9 kHz** on four windows. Those giant phantom peaks were the absolute floor flattening the roll-off into an apparent plateau: after the fix **every one of them is gone**, the 16 kHz and 8 kHz bins empty, and v2 drops from **104 bands / 388.8 dB to 96 / 349.7**. The **12-band cluster at 11.3 kHz survives unchanged** — that one is the trend failing on the roll-off, not the floor.
- **Corrections on a filter slope are refused (`skipReason: 'bandwidth_edge'`).** `air` is a fixed 9–16 kHz dip-scanned band, so on a file whose content stops lower it lifts the roll-off — six +6.0 dB boosts at 14.8–16 kHz on the real corpus, every one pinned at 2× cap. Guarded by local slope, and the separation is enormous: false boosts sit at **−56 to −62 dB/octave**, real deficiencies and clean spectrum at **−5 to −9**. Nothing in between, so the 25 dB/octave threshold's exact value does not matter. Applies to cuts as well as boosts (a feature on a filter slope is a filter artefact whichever way the correction points) and takes v1's bandwidth family to **zero** invented bands with detection unchanged. This one touches shipping code; it only ever suppresses. **Confirmed on the real corpus, which is where the bug was found:** v1 goes from **95 bands / 336.6 dB to 89 / 289.4 dB**, the 16 kHz histogram bin disappears entirely, and **risky boosts above 3 kHz go from six (+36 dB, all at 14.8–16 kHz) to zero** — v1's largest remaining boost anywhere on 31 windows of finished audio is +3.3 dB at 1.5 kHz. This is the only change in the whole spike that has been validated on both corpora and shown to help on both.
- **Three ground-truth-free checks (`npm run robustness`, `npm run robustness:real`).** Invariance (gain and polarity must change nothing — anything under 100% is a bug; window shifts held to a lower bar), convergence (apply a detector's own corrections, re-analyse — a detector reading the voice has little left to say), and direction (boosts above 3 kHz, where a lift adds the very defects users come to remove). They work on any audio, annotated or not. **All three detectors pass everything on the synthetic corpus** — which is a finding about the corpus, not the detectors: it cannot exercise these either. **On the 13-file real corpus they separate, and one of them found an actual bug:**

  | on finished masters | v1 | `v1trend` | v2 |
  |---|---|---|---|
  | exact invariance (min) | **100%** | **100%** | 89% — a bug, now fixed |
  | framing invariance (mean) | 99% | 97% | 95% |
  | convergence, median residual | 0.11 | **0.00** | 0.24 |
  | risky boosts >3 kHz | **0** | **0** | 5, +18.3 dB |

  Three findings. (1) **v2 is not invariant to gain or polarity on one file** (`bk_HarryPotter`, 89%) — a transformation a magnitude spectrum cannot see changed its answer, which is a defect by definition rather than a tolerance. (2) **`v1trend` converges completely** where v1 leaves 11% and v2 leaves 24% of its gain still wanted after applying its own advice — a detector chasing structure in its own reference never settles, and this is the cleanest evidence yet that the trend is reading the voice rather than the baseline. (3) The direction check confirms the slope guard on real audio and re-confirms v2's de-essing-undo problem from an independent angle.
- **The v2 invariance bug WAS the absolute epsilon — found, fixed, and the fix is behaviour-neutral.** Both detectors floored their log-power spectrum with an absolute `+ 1e-10`. Bins below the constant get flattened up to it and bins above keep their value, so which side a bin falls on **moves when you apply gain**: the same recording, 6 dB louder, produced a different envelope. Now a floor **120 dB below each frame's own peak** (`logPowerSpectrum` in `analysis.js`, shared by both detectors — they had separate copies of the same constant), which scales with the signal and is exactly scale-invariant. Verified: doubling the input moved envelope bins by between 6.02 and 10.3 dB before, and by exactly 6.02 everywhere after. **Both scorecards are bit-identical to their recorded baselines** — v1 67% / 0.50 / 24 spurious / 79.41 dB / 0.021 aim, v2 83% / 0.67 / 4 / 7.66 / 0.015 — so this buys the invariant for nothing.
- **Two wrong attributions on the way, and the second is the reusable lesson.** I first reported the epsilon as *ruled out*, because attenuating a case to −60 dBFS and gating its pauses to −40/−80/−140 dB left all three detectors at 100%. Both probes were bad. (1) They ran **end to end through the bands**, where a defect is only visible once it is large enough to change a decision — so the bug hid on every synthetic case while breaking a real file. (2) The gate depths **straddled past the failure**: the error is non-monotonic in level, peaking where the quietest bins sit near the constant, so −40 and −140 both read clean while −60 and −90 would not have. Measuring the property at the layer that must hold it (`test/voicerx/scale.test.js`) catches it on **6 of 7 signals including ungated audio** — the absolute floor broke invariance on ordinary material too, it just never moved a band there. **Assert invariants at the layer that owns them, not through the pipeline that consumes them.**
- **The diagnostic that made this findable.** `invariance()` records which band moved under which transformation, so the real-corpus run printed `bk_HarryPotter / gain +6 dB / differs: 12140Hz −2.9 (base only)` instead of "89%". A band at the top of the spectrum vanishing when the file gets *louder* named the mechanism in one line — a percentage alone is unchaseable by anyone without the file, which for a gitignored corpus is everyone.
- **The repeatability gap was mostly denominator arithmetic — measured, resolved.** A per-file fraction charges a quiet detector more for the same absolute mistake (one stray band out of two is 50%, one out of five is 80%), which is exactly the shape of v1 at 2.87 bands/window against `v1trend` at 1.55. Adding a pooled fraction and an **absolute count of bands that failed to recur** settles it:

  | | per-file avg | pooled | bands that failed to recur, per file |
  |---|---|---|---|
  | v1 | 75% | 74% | **0.78** |
  | `v1trend` | 56% | 50% | **0.89** |
  | v2 | 55% | 55% | 1.44 |

  In absolute terms `v1trend` fails to reproduce **0.11 more bands per file** than v1 — not the 19-point collapse the fraction implied. It is genuinely a little less stable *per band emitted*, and it emits far fewer bands, so the number of findings a user sees change between two runs of the same file is about the same for both. **v2 is unambiguously worst at 1.44**, nearly double v1's, and that is the one number the epsilon fix did not improve.
- **Real-corpus tooling is ready and waiting for files** (`npm run scorecard:real`). It runs every detector over several windows per file and reports what each claims about audio a professional has already signed off, plus v2's **mask health** (was a noise floor measurable, what fraction of 60 Hz–16 kHz reads as live, median speech-band SNR). There is deliberately no pass/fail and no baseline: nobody knows what a finished master *should* report, and a finished file may legitimately carry a notch. Read it, do not gate on it.
- **v2's open problems (still do not ship it):** (1) **Low-frequency detection is poor** — planted defects at 180, 200, 220, 300 and 400 Hz are all missed. A defect centred on the spectrum's own maximum is near-invisible to any smooth reference (a +12 dB peak at 300 Hz leaves 2.25 dB of residual), and below F0 there is no spectrum to build context from. Measured, inherent to the approach, not tunable. (2) **`IMPLAUSIBLE_DEFICIENCY_DB` is the weakest constant in the design** — separating a fillable dip from a report-only notch rests on a **1.25 dB margin** in residual height, and the same −6 dB dip reads 3.29 dB at 2.5 kHz or 6.16 dB at 1.6 kHz depending only on local spectral shape. Two better discriminators were tried and failed (wider-scale depth widens the gap only slightly; per-frequency SNR deficit is *inverted*, because an EQ cut applied to a finished file attenuates its noise floor along with the voice). Finding a real discriminator is open. (3) Recovery spread is 0.41 — better than v1's 0.58, still not consistent. (4) **No real-file validation beyond one clip.** (5) **A deep notch perturbs the trend far past itself** — an 18 dB notch at 5 kHz on an otherwise clean synthetic makes v2 emit a spurious −3.6 dB band at 9.6 kHz, where the clean version emits nothing. The mask excludes low-SNR bins but a notch still has SNR, so the notch sits inside the fit window and drags the local trend down; the recovery above it then reads as a hump. Structurally the same failure as the one that started this work, one layer up.
- **The holes patch is frequency-dependent and does not generalise.** Measured: a −20 dB notch at 5 kHz is caught, but the same notch at **800 Hz produces no hole at all** and two phantom cuts totalling 11.1 dB. `min` of the two shoulders is slope-invariant for *rejecting* a monotone slope but slope-*biased* for measuring depth — on a falling spectrum the upper shoulder sits lower, under-reading the notch by roughly the slope across the window, which at 800 Hz is enough to fall under `MIN_DEPTH_DB`. This is evidence for replacing the approach rather than adding a fifth guard.
- **Known remaining weakness in both client and server:** the chord baseline also misreads pure *curvature*. A steep convex roll-off with no notch anywhere near it leaves the envelope above the chord across the whole region and reads as a hump. Fixing it means replacing the two-point chord with a curvature-robust local fit, which recalibrates every region on every file — deliberately not bundled with the hole fix.
- EQ and VoiceRx are **separate plugins with separate band pools and separate nodes in the live chain** (VoiceRx first — corrective before creative). They were built as two views onto one pool; in use, role bands and hand-placed bands sitting in one list looking alike but behaving differently was the problem, not the solution. The only link left is a one-way hand-off: VoiceRx can **move** its corrections into the EQ, where they become ordinary untagged bands. Moving rather than copying makes double-application structurally impossible. See `src/composables/useEqInstance.js`.
